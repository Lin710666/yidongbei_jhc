## 7.0 相对 1.3 改了什么

这一版做了四件事：**加一个新形象、加离线重连、优化启动、做成能装机的桌面软件**。

### ① 新 Live2D 形象（`hanfu`）

用 `ComfyUI-See-through` 把一张汉服立绘拆成 24 个语义图层
（眼白 / 瞳孔 / 睫毛 / 眉毛各自左右分离，还有嘴、鼻、脸、前后发、上下装……），
再用 `PSD2Live` 生成 Cubism 模型，在「外观」页可选。

```
public/models/hanfu/
  hanfu.moc3 / hanfu.model3.json / physics3.json / cdi3.json / 4 个动作
  hanfu.4096/        3 页贴图
  _source/           cmo3 工程文件与 psd2live 报告（便于日后精修）
```

30 个 drawable、18 个参数、九轴面部经纬网、头发与眼球物理。
授权说明见 `借物表.md`（原画素材源自网络，仅本机演示）。

### ② 离线重连（两版都有）

原来后端是本机 FastAPI 服务，**它没起来或中途重启时，前端直接抛错** ——
用户只看到"请求失败"，既不知道要等也不知道该做什么。

现在加了 `public/js/wenlv-net.js`：

- 请求失败（网络错误 / 5xx）时进入重连态，页面顶部出现
  **「连接已断开，正在重连…（第 N 次）」**
- 按指数退避持续探测（1s→2s→4s，上限 8s），不会疯狂打请求
- 恢复后横幅变绿提示"已重新连接"，并**自动补拉**启动时失败的那批数据
  （能力清单、视频清单、状态灯……），用户不用手动刷新
- 也监听 `online`/`offline` 事件，覆盖网卡层面的断网

探测打的是新加的 **`/api/ping`** —— 它不做任何外部调用，毫秒级返回。
不能用 `/api/status`：那个要探 Ollama，本机没启动 Ollama 时要等满超时。

### ③ 启动与流畅度优化（都有实测数字）

| 项 | 改前 | 改后 |
| --- | --- | --- |
| `/api/status` 响应（Ollama 未运行时） | **4040 ms** | **153 ms** |
| `/api/ping`（新的轻量探测） | — | 2 ms |
| 启动时数据加载阶段 | 11 个请求**串行** | 并行（`Promise.allSettled`） |
| 页面数据就绪 | — | **848 ms** |

`/api/status` 那 4 秒的根因：Ollama 没运行时 `httpx.get` 到 11434 会**等满超时**
（先试 IPv4 再试 IPv6 各等一遍 = 2 秒），而这个接口一次刷新要探两次。
修法是先做 0.15 秒的 **TCP 端口预检**（端口没监听就立刻返回）再加缓存，
见 `backend/app/llm/client.py` 的 `_tcp_open()` 与 `local_ready()`。

### ④ 桌面软件版（一键安装）

`desktop/` 下是一个 Electron 外壳，把后端用 PyInstaller 打成自包含 exe，
再配上前端一起封进 Windows 安装包：

```
双击 desktop\打包桌面版.bat   →   desktop\dist\智能文旅辅助系统-<版本>-安装包.exe
```

**装完就能用，目标机器不需要装 Python、不需要开命令行。**
安装包约 130 MB，自带 Electron 运行时 + 后端 + 全部前端与模型素材。

安装包本体**没有进仓库**：130 MB 超过 GitHub 单文件 100 MB 的硬上限。
仓库里放的是源码 + 一键打包脚本，跑一次就有了。
详细设计与已知限制见 [`desktop/README.md`](desktop/README.md)。

### 1.3 相对 1.2 改了什么

**交通费虚高**（用户反馈："杭州到上海会默认从杭州打车去上海"）。查下来不是单个
bug，是**四层叠在一起**，每层都能单独把预算推高：

| 层 | 问题 | 后果 |
| --- | --- | --- |
| ① 计费方式 | `_transport()` 只要两点 >1.5km 就一律取高德的 `taxi_cost`（**打车费**） | 40 公里的跨区、甚至城际都按打车算 |
| ② 餐厅选址 | 餐厅按天数轮换（`restaurants[i % len]`），**完全不看位置** | 排出"在松江玩完、打车 40 公里回人民广场吃饭"，那一段 138 元 |
| ③ 景点分天 | 按相关度顺序**按个数切片**，没有地理聚类 | 同一天横跨 40 公里 |
| ④ 往返大交通 | 拍脑袋的固定值（高铁一律 150/人），**而且从来没读过「出发地」** | 杭州→上海和杭州→乌鲁木齐估得一样；**同城游也收 600 元** |

修法与实测见下面「[交通费为什么虚高](#交通费为什么虚高已修)」一节。效果：

```
成都4天   交通 1468 →  487.8    总预算 8548 → 3661.8
苏州2天   交通  112 →   24.3
杭州1天   交通   16 →    4.0
杭州→上海（165km，2人往返）  固定 600 → 293.4（真实高铁 73×2×2 = 292 ✅）
同城（出发地=目的地）        凭空 600 → 0
```

顺带把每天的景点排成了**地理连贯的片区**，餐厅也从"轮换"改成"就近"
（出现「文殊院 + 文殊院美食街」这种合理搭配）。

## 快速开始（新用户看这里）

### 第一次用：三步

```
1. 双击  检查环境.bat     ← 先看看缺什么（只检查，不改动任何东西）
2. 双击  install.bat      ← 装依赖
3. 双击  start.bat        ← 起服务，会自动打开浏览器
```

浏览器打开 <http://localhost:8000>。

> 也可以直接跳到第 2 步，但**先跑一次 `检查环境.bat` 能省很多时间** ——
> 它会把「缺 Ollama / 缺模型 / 没填高德 Key / 没装语音」这几件事一次列清楚。
> 这些缺一样，界面照样能打开，但一点生成就报错，很难猜到是哪里不对。

### 四个脚本分别在什么时候用

| 脚本 | 干什么 | 什么时候用 |
| --- | --- | --- |
| **`检查环境.bat`** | 8 步逐项体检（Python / 依赖 / Ollama / 模型 / 高德 Key / 前端产物 / 语音 / 素材与端口）。**只检查、不改动环境** | 第一次拿到项目；或界面不对劲时先跑它 |
| **`install.bat`** | 建 `backend\.venv`、装 Python 依赖、生成 `backend\.env` | 第一次，或依赖变了之后 |
| **`一键部署.bat`** | `install.bat` 的全部 + **拉起 Ollama 并下模型**（`qwen2.5:7b` 约 4.4 GB） | 想一次装齐、机器上还没有模型 |
| **`start.bat`** | 起**语音服务**（装了的话）+ **后端**，并打开浏览器 | 每次要用的时候 |

`install.bat` 和 `一键部署.bat` **只需要跑一次**（两个都跑也行，后者会认出已装好的部分）。

### 每次要用的时候

双击 `start.bat`。它会：

1. 探一下 `http://127.0.0.1:7860`，**已经在跑就不重复起**语音服务（重复起会抢端口、还白占显存）
2. 没跑就自动找语音服务的安装位置，用**最小化窗口**起一个
3. 没装语音就跳过并提示 —— 不影响其它功能
4. 起后端，并自动打开 `http://localhost:8000`

**想省显存**（语音服务和 Ollama 共用同一张显卡）：用 **`start.bat notts`** 跳过语音。
8 GB 卡上两个都开，显存只剩两三百 MB（实测 7720 / 8188 MiB），生成会变慢但能用。

**没装依赖就跑 `start.bat`** 会直接告诉你「请先双击 install.bat」，不会让你对着
`ModuleNotFoundError: No module named 'uvicorn'` 发愣。

### 怎么停

- **后端**：在 `start.bat` 那个窗口按 <kbd>Ctrl</kbd>+<kbd>C</kbd>
- **语音服务**：单独关掉那个最小化的窗口（它是个独立进程）

```

### 为什么 `.bat` 里要写 `PYTHONUTF8=1`

`pip install -e .` 写出的 `.pth` 文件里，路径是 UTF-8；而 `site.py` 读 `.pth`
时用的是系统区域代码页（中文 Windows 上是 GBK）。本项目所在路径含中文
（`移动杯项目`），于是 venv 里的 python 会在 `init_import_site` 阶段直接
fatal error，报的还是 `UnicodeDecodeError: 'gbk' codec can't decode ...`，
压根不提路径，看起来像 Python 装坏了。

`set "PYTHONUTF8=1"` 解决这个问题。**引号不能省** —— 写成
`set PYTHONUTF8=1 && ...` 会给值尾加一个空格，python 会以
`invalid PYTHONUTF8 environment variable value` 拒绝启动。

## 融合时做的几个关键决定

### 1. `/api/chat` 归原生所有，5.0 界面的 SSE 挂在 `/api/chat/stream`

两边都要「对话」，但协议不同，一个路径没法同时满足：

- **HikiTravel 原生**（组员的 React 工作台在调）一次性返回一整份 `TravelPlan` JSON
- **5.0 的 AIRI 界面**用 SSE 流式解析器读（`public/js/util.js` 的 `sse()`）

所以 `/api/chat` 保持原生 JSON 语义，5.0 那条改成 `/api/chat/stream`（界面里
`public/js/app.js` 对应改了一行）。这样两套前端各拿各的，谁都不用迁就谁。

中间试过一个捷径：让兼容层先注册、把 `/api/chat` 抢下来，原生的挪到
`/api/chat/plan`。能跑，但代价是**组员的 React 界面调 `/api/chat` 会拿到 SSE**，
对话生成直接坏掉。路径不重叠才是干净的解法。

### 2. 「文旅」面板里装的是组员的 React 工作台（整套，原生挂载）

按需求「保留 AIRI 外壳，把组员那套**整套**放进文旅面板」做的。
做法是**把 React 组件直接挂进外壳的 DOM**，而不是套一个 iframe：

- 给组员的工程**新增**了一个嵌入入口（不动他原有代码）：
  `src/embed.tsx` + `src/embed.css` + `vite.embed.config.ts`
- 用 `vite build --config vite.embed.config.ts` 打成 IIFE + 单 CSS，
  产物是 `public/planner-embed.js` 与 `public/planner-embed.css`
- 外壳里就是一个 `<div id="wenlv-planner">`，由 `app.js` 的 `bindPlanner()`
  调 `window.WenlvPlanner.mount('#wenlv-planner')`

**为什么先试了 iframe、又改回原生挂载**：iframe 里是另一个文档、另一套 body 样式，
字体/背景/配色都继承不到外壳，看起来永远是「两块拼在一起的板子」。
同一个文档里挂载才能共用外壳的字体与背景。

**没有全屏按钮**。一开始做过一个「⤢ 全屏」，按需求去掉了：工作台就该老老实实待在
面板里，不该再多一个需要用户理解的交互。（顺带说明一个当时的坑：`backdrop-filter`
会让元素成为 `fixed` 后代的包含块，所以那个全屏当时只能靠改 `.side` 实现。）

**贴合是怎么做到的**——三件事：

1. `ConfigProvider` 切 `darkAlgorithm`（原来的 antd 是浅色白卡，放进深色外壳里非常刺眼）
2. 主色取外壳 CSS 里给「文旅」语义留的那个青绿 `--wenlv`
   = `oklch(76% 0.11 178)` = **#54c8b1**，其余 token 照外壳的
   `--surface` / `--border` / `--text` 对齐（卡片底色 `rgba(255,255,255,.035)`、
   边框 `.08`，实测与外壳同源）
3. 嵌入入口**不导入** `antd/dist/reset.css`，也不导入它的 `index.css` ——
   那两个会改 body / `#root` / `h1~h6` 的全局样式，会和外壳的设计系统打架

**踩过的三个坑**：

- **`process is not defined`**：Vite 在 lib 模式（IIFE）下**不会**自动替换
  `process.env.NODE_ENV`（它假设由使用者提供），而 React 与 antd 都要读它。
  不 `define` 的话产物一加载就抛错、工作台整个挂不上去，而页面本身不报错，
  很容易误判成「没渲染出来」。产物也因此从 1.34 MB 降到 957 KB。
- **antd 的响应式断点按视口算，不按容器算**：`<Col xs={24} lg={8}>` 走的是
  CSS 媒体查询。嵌进 518px 的面板后视口仍是 1600px，于是 `lg` 命中，
  两列被压成 167px / 335px —— 表单挤成一条，比不响应还糟。（用 iframe 时没这问题，
  因为 iframe 有自己的视口，正好 518px。）改用**容器查询**后，面板多窄都自动单列。
- **antd 的 `Row gutter` 是负外边距**：`gutter=16` 时 Row 左右各 `-8px`。整页版里
  外层 padding 会抵消它，嵌进面板后外层 padding 被收成 0，这 8px 就顶出去了
  （实测容器 494 / 可视 486，横向出现滚动条）。把负边距归零即可。
- **`antd` 的 `Button` 会自动给两个中文字符加空格**：「导航」渲染出来是「导 航」。
  写断言时先去掉空白再比，否则会把已经实现的功能误报成缺失（这个我确实误报了一次）。

#### 深色化：把写死的浅色换成主题 token

组员那份 `PlanView.tsx` / `MapView.tsx` 里有几处**内联样式写死的浅色**，
自己是浅色主题时没问题，嵌进深色外壳后就是一块块白的：

| 位置 | 原来是 | 现在 |
| --- | --- | --- |
| 「换一个 / 换一家餐厅 / 选这家」的展开面板 | `#fafafa` | `token.colorFillQuaternary` |
| 实时天气预报的每一天 | `#f5f5f5` | `token.colorFillTertiary` |
| 当晚住宿那块浅绿底 | `#f6ffed` + `#b7eb8f` | `token.colorSuccessBg` + `colorSuccessBorder` |
| 地图示意图（本地画的 SVG） | `#eef3f7` + 文字 `#333` | `token.colorFillQuaternary` + `token.colorText` |
| 次要文字 `#888` / `#555` / `#999` | 写死灰 | `colorTextTertiary` / `colorTextSecondary` |
| 交通行、换一个按钮 `#1677ff` | 写死蓝 | `token.colorPrimary` |

为什么不用外部 CSS 覆盖：这些是**内联样式**，优先级高于任何样式表，
从外面压只能靠 `!important` 硬顶，太脆。换成 token 之后两个主题都对：
`colorFillQuaternary` 在浅色主题下取到的就≈`#fafafa`（他自己的界面观感不变），
`darkAlgorithm` 下自动变暗，谁都不用为对方写特例。

验收方式是"扫整棵 DOM，看还有没有**不透明的近白色背景**"——
判据刻意不是"背景必须是暗的"，因为 token 给的多是低透明度叠色
（`rgba(255,255,255,.04)` 的 rgb 是白的，叠在深底上依然是深色，那不算问题）。

```
方案生成后，把所有展开面板都点开再扫：
  检查了 17 个元素   → ✅ 不透明近白背景 0 个
  卡片底色 rgba(255,255,255,.035) / 边框 .08
  天气格   rgba(255,255,255,.08)  / 边框 .07
  外壳 body 底色 rgb(18,18,18)
```

**原版那套表单去哪了**：界面上不再展示（按需求「之前那个也不要了」），
但**元素仍然留在 DOM 里、只是 `hidden`** —— `app.js` 里大量绑定依赖这些 id
（词云点条件会回填表单、「生成 / 导出 / 朗读」按钮都挂在这些元素上），
删掉会直接报错。只有「生成结果」那个展示位留在外面可见，
词云点「营销文案 / 个性化方案」写结果前会自动把它显出来，避免结果写进看不见的地方。

### 4. 对话时把「词云上点过的条件」一起提交

组员的后端有一条既定的合并契约（`orchestrator._merge_base`）：
**结构化字段优先，对话只补缺**。他们的 React 工作台就是这么用的
（表单已填字段作为 `base` 提交）。

5.0 的聊天框原来什么都没带，于是完全依赖 LLM 意图解析 —— 而那个解析器对
中文数字不敏感（「两天 / 两个人」都认不出）。这里把 5.0 侧也接到同一条契约上：

- 取 `cloud.getSelected()`，也就是**用户真的在词云上点过**的词
- 按 capabilities 里这些词的 `payload` 映射成 HikiTravel 的画像字段
- 只有一处例外：天数还要看用户有没有亲手动过天数控件（拖滑杆 / 点箭头），
  动过就以控件当前值为准

那是默认值不是用户填的。全送上去的话，用户在聊天框说「帮我排苏州三天」
会被默认值盖成「杭州 2 天」，比不合并还糟。所以只认点过的词。

顺带修掉一个我自己的渲染 bug：方案标题原来写的是
`params.get("city") or "目的地"`，而对话那条路 `params` 是空的，
于是聊天生成的方案标题会变成「**目的地** · 4 天3晚 个性化方案」，像模板没填。
`TravelPlan` 本身没有 `destination` 字段，改成按
「点过的城市 → `summary` 开头的城市名 → 各日 POI 多数决」依次推导，
并去掉高德返回的「市」后缀（杭州市 → 杭州）。

多数决这一步不是多余的：实测一份苏州方案里 Day 1 排的是上海豫园与外滩，
取「第一个 POI 的城市」会把标题写成上海市。

### 5. 结果卡排版是硬契约

`app.js` 的 `layoutResultBlock()` 靠 **H2 标题的文案**决定排版：
`行程总览` / `费用预估` 各占一整行，`## Day N` 那几块横着排成一行，
`版本 A` / `版本 B` 排成两列。所以 `_render_plan_markdown()` 输出标题时
一个字都不能改，否则排版就散了。

### 6. 角色卡用深合并，不用 5.0 的浅合并

5.0 的 `lib/cards.js` 是 `normalize({...patch, ...input}, base)`：patch 里带了
`voice` 键，整个 `voice` 对象就被替换，缺失字段回退到**默认值**而不是原值。
后果是只发 `{voice:{speaker:'vivian'}}` 时，`voice.instruct` 会被清空——
用户挑完音色，刚写的语气描述就没了。

`cards_store.py` 改成递归深合并：patch 里出现的字段才覆盖，明确传 `null`
仍然能清空。表达力没变弱，只是不会误删。

### 7. 没接入的可选功能，统一返回 501 + 一句人话

全景图、图片转 3D、Blender 联动、视频背景、我的音色、语音识别（STT）
和语音合成（TTS）都是 5.0 的独立服务，融合版没有带过来。这些路径在 5.0 里
存在、前端也照样会调，缺了就返回 404 —— 用户看到裸的 `HTTP 404`，
分不清「这个功能本来就没有」还是「程序坏了」。所以显式声明 501 并写清原因，
前端 `api()` 会把这段文案原样弹出来。

### 8. 前端资源自动带版本号，改了就必然失效

`StaticFiles` 只发 `Last-Modified` / `ETag`，**不发 `Cache-Control`**，
浏览器于是按「启发式缓存」自己算一个新鲜期（常见做法是文件年龄的 10%），
在那段时间里直接吃本地副本、连问都不问服务器。

改前端的时候这会踩得很惨，而且症状极具误导性：`index.html` 是新版
（所以界面上出现了新按钮），而**同一次改动里的 `app.js` 还命中旧缓存** ——
页面就成了「按钮在、点了没反应、面板一片空白」。改的人只会以为代码写错了，
其实服务器上的文件完全是对的。（这个我真被绕进去过一次，还是看主人的截图才发现的 ——
我只用无头浏览器自测，无头每次都是全新会话、永远命中不到缓存，所以永远测不出来。）

做了两层防护：

**① `main.py` 加中间件**，对**非 `/api` 路径**一律加
`Cache-Control: no-cache, must-revalidate` —— 浏览器每次都带 ETag 回来问一次，
没变就 304，变了就拿新的。`/api/tile` 的瓦片缓存（`max-age=86400`）不受影响。

**② 首页的资源 URL 带版本号**（这层才是真正兜底的）。
`index.html` 里自己的 css/js 都写成 `?v=__ASSET_V__`，
`main.py` 的 `index_html()` 在每次返回首页时，用 **`public/` 下最新的文件修改时间**
替换掉这个占位。任何前端文件一改，所有资源 URL 立刻变化 → 缓存必然命中不了。

```
改动前  /js/app.js?v=1789837582
改一下 app.js 后（不改任何配置）
        /js/app.js?v=1789837785   ← 自动变了
```

所以**不需要任何人手动清缓存、也不需要手动维护版本号**。`vendor/` 下的
第三方库不加版本号（体积大又不会变，没必要每次重下）。

顺带一条工程教训：**面板不允许"一声不响地空白"**。空白的容器既可能是"还在加载"、
也可能是"脚本没到"、也可能是"React 渲染崩了"，三种情况长得一模一样，
排查成本极高。现在：

- `#wenlv-planner` 里写死了「正在载入行程规划工作台…」，挂载成功才被 React 顶掉
- 脚本标签带 `onerror`，把加载失败记下来
- `mount()` 外面包 try/catch，渲染期抛错另外用 `window.onerror` 接
- React 里加了 ErrorBoundary（渲染期的错不会被 try/catch 接住）
- 每条失败路径都把**具体原因写进面板**，而不是留在 console 里

### 9. 词云点选的条件同步进工作台（外壳与工作台之间的桥）

「文旅」面板换成组员的工作台之后，词云就成了"半截"的界面：它原来把点选的
**目的地 / 预算 / 同行人群 / 兴趣 / 饮食禁忌**填进右侧面板的表单，
而那张表已经被 `hidden` 收起来了。实测确认：

```
点「杭州 / 舒适 / 亲子 / 美食」
  旧表单（hidden，看不见）：城市=杭州  人群=亲子  兴趣=自然风光·人文历史·美食·亲子
  工作台（可见的那张表）：全部为空          ← 点了等于没点
```

只有底下一行字幕飘过「记下了：…」。所以加了一层桥（`frontend/src/bridge.ts`）：

- **条件词 → 工作台表单**：外壳把 payload 翻译成工作台的字段名送过去
  （`city→destination`、`days→duration_days`、`budget 档位→元`、
  `crowd→adults/children/elderly`、`interests→preferences`、`diet→dietary_restrictions`），
  工作台的表单订阅后写进 antd Form。用户点完当场看得见。
- **「个性化方案」→ 工作台生成**：平时模式下这一下交给工作台按表单生成
  （走 `POST /api/plan`，结果直接长在表单下面，能改景点 / 换餐厅 / 看地图），
  不再在下面另开一块旧样式的输出区、两边各出一份。
  **但全屏词云下例外** —— 那时右侧面板整个是藏起来的，工作台看不见，
  交给它生成用户会以为"点了没反应"，所以全屏仍走舞台上的结果卡。

三个容易踩的点：

1. **多选组不能只送当前点的那个词**。词云的「兴趣 / 饮食禁忌」是多选，
   点一下只有一个词条的 payload；直接覆盖会把前一个抹掉，而用户看到的词云上
   两个都还亮着。所以按 `cloud.getSelected()` 算出这一组当前选中了什么，整组同步。
2. **两边的词表不一致**。词云有「文艺打卡 / 购物」，工作台原本没有这两项；
   「忌辣」在工作台里叫「无辣」。所以给工作台补了选项、并加了一张同义词表
   （`忌辣→无辣`）。不补的话，同步过去的值在下拉里找不到自己。
3. **antd 的 `setFieldsValue` 不触发 `onValuesChange`**。要手动回调一次 `onChange`，
   否则 PlannerPage 里那份「表单已填画像」（对话生成时当底稿用）会跟界面对不上。

验证（`verify-wc-bridge.mjs`），点一个词看一眼表单：

```

点杭州     : 目的地=杭州   天数=2
点舒适     : 目的地=杭州   天数=2  预算=3000
点亲子     : 目的地=杭州   天数=2  预算=3000  成人=2  儿童=1  老人=0
点人文历史 : …  兴趣=[人文历史]
点美食     : …  兴趣=[人文历史+美食]      ← 多选没丢
点素食     : …  忌口=[素食]
点忌辣     : …  忌口=[无辣]               ← 同义词映射
点「个性化方案」→ POST /api/plan（工作台自己的链路）30s
                  方案出在工作台：「杭州2日适中人文历史·美食游」，用的正是刚点的条件
                  旧输出区字符数 0（没往旧链路写）
全屏词云下点「个性化方案」→ 仍走 /api/wenlv/generate，结果卡两天并排 ✅（原行为未退化）
```

### 10. 词云换成**当前项目**的词表（不再是上个项目那份）

5.0 那份词云写的是上个项目的东西：营销平台 / 文创产品概念 / 机体记忆 /
声音设置 / 角色卡 / 形象 / 输出质检 / 营销文案。本项目根本没有这些能力，
点下去要么没反应、要么点到一个不存在的东西。所以整块换掉。

新词表放在 `backend/app/data/wordcloud.json`，**每一项都有出处**，不是编的：

| 词从哪来 | 依据 |
| --- | --- |
| 条件词（兴趣 6 项 / 节奏 3 项 / 交通 4 项 / 讨厌 3 项 / 忌口 4 项 / 人群 6 项） | 组员 `PreferenceForm.tsx` 里的真实选项常量 |

| 能力词（四段式流水线 / 异常拦截 5 类 / 跳转降级 4 级 / 雨天 Plan B / 本地知识库） | 组员自己的 `docs/量化指标.md` |

规模：**16 组 / 76 词**，其中默认显示 19 个（`role` 为 `label` 的组标签 +
`core` 的核心动作词，其余 `member` 默认压淡，点组标签才展开）。
顺带修掉两个跟着一起错的字段：`entityCount` 原来是 5.0 样本库的 117，
本项目的"本地样本库"其实是 RAG 那 10 条，报 117 是假话；
`features` 原来写的是 5.0 的四大能力，换成本项目真有的六项。

**产物词点下去会真的带路**：新增 `focus` 动作（`frontend/src/focus.ts`），
点「实时天气」就把右侧滚到实时天气预报那块并闪一下，点「景点备选」会先把
那一行的「换一个」展开再滚过去 —— 词云从"一排入口"变成了这个项目产出的目录。

实现里踩到的三个点：

1. **按文字找元素不能取"第一个包含它的元素"**。找「实时天气预报」时，
   最外层那个容器的 textContent 也包含这几个字，结果滚到页面顶端不动
   （实测四五个目标全都停在 67px）。改成取**文字最短的那个匹配元素**才落到正确的一行。
2. **目标名不能和表单字段 id 撞**。费用明细原来叫 `budget`，而工作台表单里

### 11. 对话框的输出区里挂的是**文旅工作台本体**，不是照它画的界面

需求原话：「我要的是文旅工作台也是图二一模一样的样子在输出框里面」。

做法：把组员那套 React 组件（`App` = `PlannerPage` = `PreferenceForm` 表单
＋结果的 `PlanView` ＋ `MapView`）**原样挂进对话框的一条消息里**，
和「文旅」页签里挂的是同一棵树、同一份 `planner-embed.js`。

```

  startWorkbenchInChat()
    → appendMsg('assistant','') 造一条消息
    → el('div',{class:'workbench-host'}) 作为容器
    → window.WenlvPlanner.renderWorkbench(host)      ← frontend/src/embed.tsx
        → ReactDOM.createRoot(host).render(<App standalone />)
```

**为什么不照着画一套像的。** 之前那版是"照着工作台的问题手搓了一份气泡问答"

外壳那份不会跟着变。老板的评价是「这哪里一样了」，这个判断是对的。

### 启动耗时：修掉一个导入期的 42 秒

原来 `import app.main` 要 **42.1 秒**。uvicorn 迟迟不打印启动横幅，

1. 索引改成**首次 `search()` 时才建**（懒加载）—— 导入立刻降到毫秒级
2. embedding 换 **批量** `/api/embed`，往返次数从 N 次降到 1 次
3. 两个路由共用同一个 `get_orchestrator()` 实例

```
改前  import app.main          42.10s
改后  import app.main           0.51s      （82 倍）
首次 search（建索引一次）        6.16s
第二次 search（走缓存）          2.09s
```

### 对话里的「两天 / 两个人」解析不出来（组员的解析器，未改）

这个会直接被评委看见，所以放最前面。输入
**「帮我规划杭州两天，两个人，喜欢人文历史」**：

| 字段 | 期望 | 实际 |
| --- | --- | --- |
| 天数 | 2 | **1** ❌ |
| 人数 | 2 | **1** ❌ |
| 目的地 | 杭州 | 杭州 ✅ |
| 兴趣 | 人文历史 | 人文历史 ✅ |

实测稳定复现（连跑两次结果一致，不是随机），而且**两条解析路径都有这个盲点**：

- **LLM 抽取路径**（首选，`intent_skill.py` 的 `chat_json`）：目的地和兴趣都抽对了，
  唯独漏掉天数与人数 —— 说明是提示词/字段说明的问题，不是模型不行
- **规则兜底路径**（`_rule_parse`）：
  - 天数用的是 `r"(\d+)\s*天"`，**只认阿拉伯数字**。`两天` / `三日游` / `玩三天`
    全部匹配不到（`2天` 能匹配）
  - 人数用的是 `r"(\d+)\s*人"` 加一张关键词表 `情侣|夫妻|两口子|二人|两人|双人`
    —— **「两个人」不在表里**，同样漏掉

中文里「两天两晚」「三个人」是最自然的说法，所以这个盲区影响面很大。
修法不复杂（正则加中文数字映射 + 提示词里明确「中文数字也要转」），
但这属于组员的 intent skill，**按主人的意思没有去动它**，改成在融合层做适配
（见「关键决定 4」）：界面上点过的条件会作为结构化字段提交并优先于解析结果，
所以**走词云/表单那条主路径不受影响**；只有「纯在聊天框里打中文数字」才会露出来。

5. **记忆库没接**：`/api/memory*` 返回结构正确的空壳（`total: 0`），
   界面上「记忆 0」是如实显示，不是坏了。
6. **语音合成/识别没接**：`/api/tts` 返回 503 并提示原因（前端对 502/503/504
   有专门的文案分支），`/api/stt` 同理。
7. **React 工作台是构建产物**：`public/planner-embed.js` 与 `.css` 是
   `vite build` 的结果。改 `HikiTravel/frontend/src/` 之后要重新构建并拷回来，
   命令见「重新构建并更新工作台」一节。
8. ~~**boot 还没跑完就发消息，回复会被整条清掉**~~ —— **已修**
   `app.js` 的 `renderHistory()` 排在 `boot()` 的十几个 `await` 之后；
   它原来一执行就 `log.innerHTML = ''` 再按 `S.history` 重建。
   助手那条流式回复是**直接写进 DOM 的**，流没结束前不在 `S.history` 里，
   于是这一清就没了 —— 界面上表现为"我说了话，它忙了一会儿，什么都没回"。
   实测（`.verify-tools/probe-chat-dom.mjs`，MutationObserver）：

   ```
   + msg me      你好，你能做什么？
   + msg         🤖                          ← 流式容器（空）
   + msg sys     🤖 正在理解需求，并检索真实景点与天气…
   - msg me      …三个节点被一起删掉…
   - msg
   - msg sys
   + msg me      你好，你能做什么？            ← 只按 history 重建，助手回复不在其中
   ```

   触发窗口有多大取决于 boot 有多快：本机常态约 **5 秒**内（15 个 `/api` 调用
   在 4.8 秒内返回）。但**只要有一条 `/api/chat/stream` 在飞，后端是串行的**，
   boot 会被拖到 30 秒以上，窗口就跟着变宽（实测 30 秒时发消息必触发）。

   **修法**（`app.js` 的 `renderHistory()`，约 1245 行）：只在**日志还是空的**
   时候才铺历史，日志里已经有东西就直接返回。

   判据刻意用"日志非空"而不是 `S.busy` —— 因为 `S.busy` 只覆盖闲聊那条路，
   方案那条（`runPlanWith`）既不设 busy、也不把结果写进 `S.history`，
   同样会被这次重建抹掉。而 `renderHistory()` 全程只在 `boot()` 里被调一次，
   所以"日志非空"只可能意味着"已经有实时内容了"。

   代价是这一种情况下**少铺一次历史**（刷新页面就正常了）——
   宁可少铺一次，也不冒抹掉用户内容的风险。

   （**不要**把 `renderHistory()` 简单往前挪到 `loadHistory()` 后面：
   它排在原处是为了等 `loadCapabilities()` → `setActiveCard()` 把角色卡读进来，
   早搬会让历史消息用上默认头像 🤖 / 名字 AIRI。）

## 改清单 JSON 不用再重启了

`backend/app/data/` 下这几份清单（`capabilities` / `backgrounds` / `models3d` /
`tts-speakers` / `geo` / `wordcloud`）原来是**模块导入时读一次就定死**的，
改完必须重启服务才生效 —— 表现出来特别迷惑：文件明明改了、JSON 也合法，
接口里就是"看不见"（实测踩过好几次，一度以为模型没装成功）。

现在 `ui_compat.py` 里有个 `reload_manifests()`：相关接口每次请求前对一下
文件的 mtime，变了就重读。**改完刷新页面即可**，不用重启。

- 兜底/排查用：`POST /api/reload-manifests` 会强制全部重读，
  返回 `{"reloaded": [...]}`，看里面有没有你想改的那份。
- 解析失败的清单**不会被空壳顶掉**（半截文件写坏了也不会把现在能用的那份弄没）。
- 注意**静态资源**（`public/`）本来就是按请求读盘的，一直不用重启。

## OpenClaw 适配（Agent 引擎那条路）

赛题要求「基于 AI Coding **或 OpenClaw 引擎规范**」开发 Skill 系统，所以本项目两条腿：
网页那条是给人看的确定性演示；这条是给 Agent 引擎调的。

三块东西：

| 组件 | 位置 | 作用 |
| --- | --- | --- |
| 技能包 | `.agents/skills/wenlv-assistant/` | `SKILL.md` + `references/` + `scripts/`，符合 AgentSkill / OpenClaw 规范 |
| 确定性脚本 | 同目录 `scripts/generate-plan.js`、`scripts/generate-marketing.js` | Agent 通过 `exec` 调它们 |
| 两个纯文本接口 | `backend/app/routers/ui_compat.py` 的 `/api/quick-plan`、`/api/quick-marketing` | 脚本回来打这两个地址 |

数据流：

```
OpenClaw Agent
  └─ exec: node scripts/generate-plan.js --city 杭州 --days 2 ...
       └─ GET http://127.0.0.1:8000/api/quick-plan?city=杭州&days=2...
            └─ orchestrator（意图 → 异常拦截 → 高德检索 → 规划）
                 └─ 纯文本：质检提示 + Markdown 方案正文 → Agent 原样转述
```

**为什么绕这一道、不让 Agent 直接取网页**：OpenClaw 有防 SSRF 的既定安全策略，
`web_fetch` 访问 `127.0.0.1` 会被拦
（`Blocked hostname or private/internal/special-use IP address`），
5.0 那份验证报告里记着连 `dangerouslyAllowPrivateNetwork` 也放不开。
而技能自带的 `scripts/` 由 Agent 起成本地子进程，不受这条限制 ——
这也正是规范里 `scripts/` 的用途。

> ⚠️ **融合版曾经漏了这两个接口**：5.0 里它们挂在 `server.js` 上，后端换成
> 组员的 FastAPI 之后没跟过来。后果是"看起来装了、其实跑不通"——
> 技能包装得上、`openclaw skills info` 也显示 ✓ Ready、描述也注入进了模型上下文，
> 但真正执行的那一步一跑就是 **HTTP 404**。

验证：`pwsh -File .verify-tools\verify-openclaw.ps1`
（四段：技能包合规 / 两个接口是纯文本 / 脚本跑通 / 输出完整性）

本机现状（2026-09-21 实测）：

```
$ openclaw skills info wenlv-assistant
🏔️ wenlv-assistant ✓ Ready
  Visible to model: yes      Available as command: yes
  Binaries: ✓ node, ✓ ollama
Skills (14/53 ready)
```

> 引擎里的技能是**安装时的副本**（`~\.openclaw\workspace\skills\wenlv-assistant`）。
> 改了项目里的 `.agents/skills/...` 之后要重新装一次才生效：
>
> ```
> openclaw skills install "<项目路径>\.agents\skills\wenlv-assistant" --force
> ```

### 已知的模型能力限制（不是链路问题）

7B 级模型不会主动按 `description` 触发技能。实测三种问法：

| 调用方式 | 7B 模型表现 |

## 语音合成（TTS）与形象口型

### 之前是什么状态

`/api/tts` 直接回 **503 `NO_TTS`**（"融合版没有接入语音合成"）。这不只是"没声音"，
而是把形象那条链路一起废了：

- 形象全程静音，顶栏「语音」状态灯是「语音未接」
- `live2d.js` 里那条**读音频实时频谱驱动 `ParamMouthOpenY`** 的口型逻辑
  （连"不同模型口型参数名不一样"都处理了）**永远不触发** —— 没有音频可分析
- 三个舞台的 `speak()` 都实现好了，等于线接好了没电

### 现在怎么接的

TTS 是个**独立进程**（自己的 venv、自己的启动脚本、自己的显存），
对外是 `http://127.0.0.1:7860` 上的 `/qwenapi/v1/*`。后端在
`routers/ui_compat.py` 里加了**代理**（`/api/tts`），把请求转过去、把音频转回来。

```
浏览器 ── POST /api/tts ──▶ FastAPI 代理 ──▶ Qwen TTS WebUI (7860)
                            │                     │
                            │   ◀── JSON {audio_files_base64:[...]}
                            │   base64 解码 → 缓存到 backend/data/tts-cache/
        ◀── audio/wav ──────┘
   <audio> 播放 → WebAudio Analyser 读频谱 → 驱动角色口型
```

启动语音服务：

```bat
tools\start-tts.bat
```

按「环境变量 `QWEN_TTS_HOME` → 项目根的 `qwen-tts-home.txt` →
`tools\find-tts.ps1` 自动扫描」的顺序找安装位置。本机已经写好
`qwen-tts-home.txt`（指向 `C:\Users\11702\Desktop\qwen-tts-webui`）。

### 三个实现上的坑（都踩过）

1. **这个服务返回的不是裸音频字节，是 JSON**：
   `{"audio_files_base64": ["<base64 wav>"], "info": "成功生成 1 个音频文件, 耗时: 15.51s"}`。
   直接拿 `r.content` 当音频返回，前端 `<audio>` 会收到一坨 JSON ——
   **而且不报错，只是静静地不出声**，比 500 还难查。
2. **`info` 里带中文，不能塞进响应头**。HTTP 头只允许 latin-1，
   Starlette 一编码就抛 `UnicodeEncodeError` → 整个请求 500。
   而那个 500 特别迷惑：**合成其实成功了、缓存也写进去了，
   第一次 500、第二次却命中缓存返回 200**。
3. **`speaker` 必须给**。CustomVoice 模型下决定"是谁在说话"的是 `speaker`
   （内置音色 id），`instruct` 只管语气节奏、**改不了性别**；留空时后端会退回
   列表第一个 = `aiden`（男声），于是"不管选哪个预设出来的都是男声"。
   卡片的 `voice` 里没写 speaker 时，后端按 `presetId` 补（见 `_TTS_PRESET_SPEAKER`）。

### ⚠️ 显存：TTS 和 Ollama 抢同一张卡

实测（RTX 4060 Laptop 8 GB）：

```
只有 TTS 在跑              : 已用 3974 MiB / 空闲 3983 MiB
TTS + qwen2.5:7b 同时驻留  : 已用 7720 MiB / 空闲  237 MiB
```

**能共存，但几乎没有余量**，对话也会变慢（同一请求 6.7s → 8.8s）。
所以 TTS 用 0.6B 那一档（`_tts_pick_model` 优先挑名字里带 `0.6B` 的），别换 1.7B。
演示要抢速度时，关掉一个。

### 文本驱动的"假口型"

TTS 是**等整段文字生成完**才开始合成的（几秒到几十秒），而字幕是**从第一个字**
就开始往屏幕上吐的。这段时间里嘴不动，看起来就是"它在念稿但没张嘴"。

所以**两个舞台**（`live2d.js` / `stage3d.js`）都加了 `talkTo(text)` /
`stopTalking()`：外壳流式吐字时喂文本，按约 180ms 一个字驱动口型，标点与空白闭嘴。
**真音频一旦就绪，`speak()` 接上 Analyser 会自动接管**（舞台内部按
`analyser > talking` 的优先级分支，两套不用切换代码）。

实测（`verify-talksync.mjs`，直接采样 `mouthOpen`，不靠截图猜）：

```
不说话时           最大开口 0.000                        ✅ 嘴是闭着的
一次喂一段中文     最大 0.840 / 平均 0.481 / 24 种取值    ✅ 在动
流式追加（10 段）  最大 0.820 / 平均 0.517 / 33 种取值    ✅ 一直在动
stopTalking 之后   最大开口 0.000                        ✅ 已闭嘴
```

实现上的一个坑：文本是**流式**来的，两段之间隔几百毫秒；
如果让"攒下的时间额度"一次烧完，新一段到了会被瞬间"读完"、嘴反而不动。
所以额度封顶到一个字的量（`if (talkAcc > CH) talkAcc = CH`）。

### 形象的其他改进

- **Live2D 补了触屏视线**：原来只监听 `mousemove`，而项目面向的
  **展厅大屏基本都是触屏** —— 手指划屏幕，人物眼睛一动不动。
  改成 `pointermove`（`stage3d.js` 本来就收 pointer 事件，两套舞台行为从此一致），
  并在 `pointerup` / `pointercancel` 上把视线收回正前方。
- **两个国风模型瘦身**：纹理 8192×4096 / 8192×8192 降到 2048，
  **11.1 MB → 0.9 MB、12.5 MB → 1.2 MB（共省 21.5 MB）**；
  目录也从 `<name>.8192/` 改名成 `<name>.2048/` 并同步改了 `model3.json`
  （不改名的话目录名会一直撒谎）。降采样前后画布指标一致（覆盖 9%/α23、11%/α27）。
- **把两个模型里躺着没被引用的表情和动作挂进了 `model3.json`**：
  作者的 `FileReferences` 里既没有 `Expressions` 也没有 `Motions`，
  磁盘上那 11 个 `.exp3.json` 和 1 个 `.motion3.json` 引擎根本不知道。

  > ⚠️ **但那些"表情"不是情绪，是零件开关 —— 而且文件名会骗人。**
  > 它们写的是 `Param38` / `ParamCheek` / `Param143` 这种零件编号。
  > 实测应用 `lian hong`（文件名意思是"脸红"）之后，人物是**闭上了眼睛**，
  > 根本不是脸红。所以**只挂原始拼音名、不挂 `blush`/`happy` 这类语义别名** ——
  > 挂个名字说"这是害羞"、按下去却是闭眼，比不挂更糟。
  >
  > 这同时意味着「回复内容 → 表情」这条优化**在这两个模型上没有可驱动的东西**。
  > 想做真正的情绪表情，得换一个自带语义表情的形象：
  > VRM 那套 `happy/angry/sad/relaxed/surprised` 是标准表情，或者专门定制的 Live2D。

## 大屏展示模式与默认形象

### 「大屏」= 只切布局（手动进），而"进对话页默认"要的是另一样

这两件事被我混过一次，记清楚：

**① 「🖥️ 大屏」（kiosk）** —— 顶栏那个按钮，**手动点才进**。
进去之后顶栏与人物条藏掉、舞台铺满、底部对话栏保留。它**不请求浏览器全屏**
（见下面那段"反馈了两轮"的说明）。

**② 从开屏点「对话页」进来** —— **不**进 kiosk，而是把**对话输出区收回默认大小**。
用户要的"大屏"是这个：**顶栏在、人物条在、底部面板矮矮一条、人物占满一屏**。

- 一开始我把它做成了"自动进 kiosk"（以为大屏=kiosk）→ 用户说
  「点进去还要 esc 才能到我需要的这个大屏」，因为 Esc 正好把 kiosk 退掉。
- 真正的差别在**底部面板的高度**：`.side` 在放大态（`chat-tall`）占 **56%** 屏高，
  人物被压在中间一小块；收回默认只占 **30%**，人物才铺得开。
  实测数字：`sidePct 56% → 30%`。

实现上有个坑：光调 `WenlvChatPane.collapse()` 不够。**工作台表单是进入时默认就挂进
输出区的**（`startWorkbenchInChat`），挂完它会 `autoExpand()` 一次，把刚收起来的面板
又顶开（实测：点进对话页后 body 从 `tools-collapsed` 变成 `tools-collapsed chat-tall`）。
所以 `collapse()` 还要置一个 `entryCompact` 标记，让**那一次**自动放大跳过；
真出方案时该展开还是展开（`runPlanWith` 那条路不看这个标记）。

- **彻底不请求浏览器全屏**。这件事反馈了两轮才做对：
  1. 最初 `setKiosk()` 里带着 `requestFullscreen()`，理由是"展厅没人按 F11"；
     用户说「我要的是这样的大屏不是全屏」。
  2. 我只把"从开屏点对话页进来"那条路改成不请求全屏，**按钮那条忘了** ——
     于是点「大屏」还是先进浏览器全屏，得按 Esc 退出来才看到大屏布局。
     用户第二次反馈：「真正的大屏根本没改，进入之后要 esc 才能退出全屏进入大屏」。

  现在 `setKiosk()` 里**一行全屏代码都没有**：大屏 = 顶栏隐藏 + 舞台撑满 +
  底部对话栏保留，地址栏和标签页该在还在。要真全屏请自己按 **F11**。
  （全项目已无任何 `requestFullscreen` 调用，可用 `grep -r requestFullscreen public/` 复核。）
- **顶栏整条 `display: none`**，不是淡出。原来是 `opacity:0` + 悬停自动亮回来，
  鼠标划到屏幕顶部就会把「🏔️ 文旅智能辅助 HikiTravel-AIRI-1.3」冒出来。
- **左上角那条「🏔️ 小文 浙江文旅向导，陪你玩得明白…」（`.char-plate`）也藏**。
  它原来**根本没被 kiosk 规则盖到**，所以大屏下一直显示着 ——
  表现就是"说好只剩人物和对话栏，上面却还挂着一行字"。
- **但右上角那排工具要留着**（设置 / 静音 / 词云开关 / 全屏放大词云…），
  保持原来"平时透明、鼠标移上去才出现"的做法：
  平时看不见 → 画面干净；移过去能露出来 → 功能还在，不用先按 Esc 才有得点。

## 旅游后端的一次体检与修复

对「意图 → 拦截 → 检索 → 规划」这条链路做了实测体检（直接调编排器跑真实画像，
不看代码猜），修掉 5 个问题。每条都有修复前后的实测数字。

### ① 贴士张冠李戴：去成都，方案里讲西湖

**实测**：苏州方案的贴士是「雷峰塔…可俯瞰西湖全景」，成都方案是
「杭帮菜代表有西湖醋鱼、东坡肉、龙井虾仁」。

根因是三处叠加：

| 位置 | 问题 |
| --- | --- |
| 知识库 | 10 条**全是杭州**（西湖/断桥/雷峰塔/灵隐寺/龙井茶），且**没有城市字段** |
| `retriever.search` | 无条件返回 `top_k`，匹配度为 0 也照塞 |
| `planner_skill` | `tips=rag_tips` —— **每一天塞同一个列表**，所以同一条贴士出现 N 次 |

**修法**：给知识库加 `city` 列（幂等迁移，老库按正文回填）→ 检索按
「目的地 or 通用」过滤 → 加相关度下限 → 贴士按天分发去重。

**实测（同三个城市）**：

```
             修复前              修复后
苏州   10 条 / 5 条重复 / 全杭州    1 条 / 0 重复（只留通用的"野导/低价一日游"防坑）
成都   10 条 / 5 条重复 / 全杭州    1 条 / 0 重复
杭州   10 条 / 5 条重复            5 条 / 0 重复
```

> 副作用要清楚：**成都、苏州 现在基本没有本地知识**（只有 1 条通用的）。
> 这是老实话 —— 知识库覆盖不到就是覆盖不到。要真正补齐得**扩知识库**。

### ② 勾「美食」把餐厅当景点排

`PREFERENCE_KEYWORDS["美食"] = ["美食街","特色餐厅"]`，而搜到的结果**一律标成「景点」**。
实测：成都方案里「马旺子·川小馆(成都太古里店)」占了一个下午的观光位，
还盖着景点专属的贴士「热门景点建议通过官方渠道提前预约」。

**修法（三层）**：

1. 按**高德自己的 `type` 字段**分类（`餐饮服务;中餐厅` → 餐厅）。
2. 按**关键词来源**分流：用"吃"的词搜出来的，只收真餐厅，商圈/步行街一律丢。
3. 加**名称兜底**：名字里带「天妇罗/火锅/餐厅…」的一律当餐厅 ——
   实测高德自己也会标错（「八潮天燚天妇罗」的 type 是 `风景名胜`）。

还要补一道**兜底检索**：勾「美食」的用户没有任何景点关键词，景点池会是空的。
兜底词用 **「热门景点」** 而不是「景点」——实测差很多：

```
「景点」     → 成都金融城双子塔 / 交子公园 / 桂溪生态公园（全是新区的公园写字楼）
「热门景点」 → 东郊记忆 / 人民公园 / 文殊院 / 武侯祠博物馆 / 大熊猫繁育研究基地 / 青城山
```

### ③ 异常拦截只拦输入、不拦输出

`guard_skill` 跑在**生成之前**，只能看用户画像。实测：成都方案估 8054 元、
用户预算 6000 元（超 34%），**`warnings` 是空的**。

**修法**：新增 `skills/output_guard.py`（`OutputGuardSkill`），在 planner **之后**再体检一遍，
产出同样走 `Conflict` 通道。它查：

| 检查 | 实测效果 |
| --- | --- |
| 超预算 | 「方案估算 8548 元，比预算 6000 高 2548 元（42%）」 |
| 门票缺价 | 「8 个景点没拿到门票价…预算里的门票按 0 计」 |
| 天数不符 | 要 4 天排了 3 天 |
| 跨城 | 行程里出现非目的地的地点 |
| 时间倒挂 | 同一天时间段不是递增 |
| **深夜正餐** | 「有正餐被排到深夜/凌晨…这一天排得太满了」 |
| 同景区拆多项 | 「周庄古镇 / 周庄沈厅」这种 |

### ④ 预算里的门票永远是 0

`tickets = sum(poi.price or 0)`，而高德的景点 POI 一般**不带 `biz_ext.cost`** →
拙政园（¥90）、周庄（¥100）全算 0，方案上写「门票 0 元」——**这是在说假话**。

**修法**：不硬编票价（那是"快变"数据，按项目原则不进知识库），
而是由输出层质检**明确告知**："N 个景点没拿到门票价，预算里的门票按 0 计，
实际会比估算高"。宁可不给数字，也不给假数字。

### ⑤ 一天排 3 个景点，晚饭排到 23 点

`per_day = PACE_COUNT["适中"] = 3`，每个景点 2.5 小时 + 两餐 + 接驳，
09:00 出发算下来必然排到半夜。实测成都 Day3 的晚餐是 **23:20-00:50**、Day2 是 21:33。

**修法**：新增 `_safe_per_day()` —— 按**当天真实可用时间**（出发 → 20:30，减去两餐）
反算一天放得下几个，再和节奏取小。必去景点仍然强制纳入（用户点名的，超时交给质检提示）。

**实测**：每天从 5 项（3 景点）变成 4 项（2 景点），结束时间
`18:16 / 18:20 / 19:59 / 20:58`，深夜正餐消失。

### 顺带加固

- `_to_recommendation` 里的 `float(cost)` **原来没有 try/except**（`_to_poi` 有）——
  高德只要哪天给某个餐厅返回非数字，整条 `/api/plan` 就 500。统一收口到 `_as_price()`。
- `RetrieveSkill` 原来共用一个 `Retriever`，换城市后索引还是上一个城市的；
  改成**按目的地缓存实例**。

## 对话历史为什么"存不下来"（已修）

**结论先说**：历史**不是完全不存**，而是**只存闲聊、不存方案对话**。
而方案对话恰恰是用户用得最多、最想留住的，所以看起来像"从来不保存"。

### 根因

`sendMessage()` 里有一段"认出城市/天数就直接去生成方案"的近路：

```js
if (cityHit || dayHit) {          // 消息里带城市名或"N天"
  appendMsg('user', text);        //  只画到界面上
  await runPlanWith(over, text);
  return;                          // ← 提前 return
}
// ↓ 只有闲聊才走得到这两行
S.history.push({ role: 'user', ... });
saveHistory();
```

而 `runPlanWith()` 从头到尾**没有碰过 `S.history`**，用户消息和方案结果都只画在界面上。

**实测抓的**：给 `localStorage.setItem` 装钩子，发「帮我排个杭州两天」之后，
那条键（`wenlv-airi/history`）**全程 0 次写入**；界面上却有两个气泡、方案也出来了。

### 修法

| 位置 | 改动 |
| --- | --- |
| `sendMessage()` 的方案近路 | 补上 `push + saveHistory`（存用户原话） |
| `runPlanWith()` 开头 | 存那句"帮我排一个方案：…"（**带上一条已是同一句时跳过**，避免和上面的重复） |
| `runPlanWith()` 方案渲染回调 | 存一条助手记录 `（已生成方案：<plan.summary>）` |

方案是 **PlanView 组件**渲染的，不是纯文本，而历史只能存文本 ——
所以助手那条存的是**摘要**：刷新后至少知道"我问过杭州两天、它给过我一版"，
正文回文旅页看。这比整段对话凭空消失好得多。

### 实测

```
修复前：发「帮我排个杭州两天」→ 等方案出来 → localStorage 0 条；刷新后界面空的
修复后：修复后 → 2 条 [user:帮我排个杭州两天, assistant:（已生成方案：杭州2日适中…）]
        刷新 → 2 条都还在，界面铺回来 2 个气泡；再发一条接着存（不重来）
闲聊路径不受影响：「你好」→ 2 条，刷新后还在 ✅
```

历史存在 `localStorage['wenlv-airi/history']`，最多 60 条（`saveHistory` 里截断）。
另外还有"分段会话"（`wenlv.sessions`）：点「新对话」会把当前这段归档、
点历史列表能整段装回来。

## 「对话」并进「文旅」，并移除底部输入框

为什么会有那份重复：默认布局（非调试）下 CSS **只显示 `#pane-chat` 一个面板、
页签全藏**，工作台所在的「文旅」页签根本看不见 —— 所以当年为了"让用户在对话里
也能填表"，往聊天流里挂了一份。这是"重复实例"的真正来源。

合并之后：

```
页签：5 个 —— 文旅 / 外观 / 记忆 / 角色卡 / 声音（「文旅」排第一且默认选中）
工作台：只剩 1 份
方案结果区 #chat-log、历史对话 #chat-hist：都并进「文旅」页签

### 工作台默认折叠

排下来约 700px —— 直接铺开会把字段切掉、还挤掉结果区。

所以加了一行开关「🗺️ 填写旅行偏好 ▸」：默认折起来，点一下铺开。
生成方案前（`runPlanWith` 里）和点「开始规划」时会**自动展开**，
否则用户点完按钮、表单还折着，看起来像"没反应"。状态存 localStorage。
分栏布局（`.debug`）下不折叠：那里 520px 宽、纵向也宽松。

### 「历史对话」那一行叠在工作台上（已修）

用户反馈：合并之后，「历史对话 / ＋新对话 / 清空」那一行出现在工作台表单**中间**，
把「兴趣爱好 / 游玩节奏」等字段压住了。

**根因不是定位，是 flex 压缩**。实测数据：

```
#wenlv-planner 的盒子高度   = 373px
它内部内容的高度            = 854px      ← 溢出 481px
```

`#pane-tools` 是 `display: flex; flex-direction: column`，工作台作为 flex item
默认 `flex-shrink: 1`，于是被**压缩**到 373px。而它的内容是**溢出到盒子外面继续画**的，
后画的 `#chat-log` / `#chat-hist` 就正好压在溢出的那部分表单上面 ——
看起来就是"那一行跑到表单中间去了"。

> 注意：只比较两个元素的 `getBoundingClientRect()` 是**发现不了**这个问题的 ——
> 工作台的盒子（425~798）和历史那一行（856~892）并不相交，
> 相交的是"溢出到盒子外面的内容"。所以第一遍排查时我判成"没有重叠"，
> 直到量了 `scrollHeight` 和 `clientHeight` 的差值才看出来。

**修法**：给工作台和历史块 `flex: 0 0 auto`，别让它们被压扁，超出的部分交给面板滚动。

**实测（修后同尺寸）**：

```
修复前  工作台盒子 373px / 内容 854px  →  溢出差 481px  ❌
修复后  工作台盒子 854px / 内容 854px  →  溢出差   0px  ✅
        #chat-log 1563~1611、#chat-hist 1621~1691，都在工作台下面，互不相交
        滚动到底后取历史那一行中心点：最上层元素 = DIV.hist（没被任何东西盖住）✅
```

`.hist` 自己也被压过（高 10px、内容 32px，标题和按钮叠一起），一起加了 `flex: 0 0 auto`。

### 这次踩到的三个坑（都是移除输入框带出来的）
1. **`#chat-char-name` 被连带删掉** —— 它在原来那个「和 小文 说说话」的标题里，
   而 `setActiveCard()` 会写它 → **切角色卡时抛异常**。已把名字挪到新的
   「文旅工作台 · 当前向导：X」标题里。
2. **`id="wenlv-planner"` 出现两次** —— 合并页签时只替换到 `<p class="sub">`，
   原来那份工作台 div 还留着。两个同 id 的容器是真 bug：`$('#wenlv-planner')`
   只取第一个，第二份永远挂着"正在载入…"。
3. **`setBusy()` 里的 `$('#btn-send').disabled = b`** —— 每次生成前后都会调，
   元素没了就抛 `Cannot set properties of null`，**把整条生成链路打断**
   （实测：词云点「个性化方案」直接失败，结果卡里只剩 14 字错误提示）。
   同类还有 `case 'vision'` 里的 `$('#file-input').click()`。都加了守卫。

### 实测

## 发布到 GitHub（流程 + 一个把克隆 `.git` 删掉的坑）

推的是 `https://github.com/Lin710666/HikiTravel` 仓库的**同名分支**
（`HikiTravel-AIRI-1.3`）。内容在**仓库根目录**（不是子目录）。

### 流程

```bat
git clone https://github.com/Lin710666/HikiTravel.git
cd HikiTravel
git checkout HikiTravel-AIRI-1.3
:: 清空工作区（只留 .git），再把产品目录的内容复制进来 —— 用 /E，不要用 /MIR
git add -A
git status --porcelain      :: 逐条核一遍，确认没有敏感文件
git commit -F 提交信息.txt
git push origin HikiTravel-AIRI-1.3
```

### ⚠️ 坑：`robocopy /MIR` 把克隆的 `.git` 删了

第一遍我用 `robocopy <产品目录> <克隆> /MIR /XD "<产品目录>\.git" ...` 同步，
**结果克隆的 `.git` 整个没了**，`git status` 报 `fatal: not a git repository`。

原因：`/MIR` = `/E` + **`/PURGE`**，它会删掉"目标里有、源里没有"的东西。
我只在 `/XD` 里排除了**源目录**的 `.git`（那本来就不存在），
于是 `/MIR` 把**目标目录**的 `.git` 当成"源里没有的多余目录"清掉了。

**正确做法**（最后实际用的）：

```powershell
# 1. 清空工作区，只留 .git
Get-ChildItem $clone -Force | Where-Object { $_.Name -ne '.git' } | Remove-Item -Recurse -Force
# 2. 复制（/E 只增不删，不会碰 .git）
robocopy $src $clone /E /XD $clone\.git ... /XF *.pyc .env qwen-tts-home.txt
# 3. git add -A —— 删除交给 git 算，不让 robocopy 去猜
```

> 好在远端是完整的：`git ls-remote` 确认 `origin/HikiTravel-AIRI-1.1` 的提交和本地克隆
> 的 HEAD 一致（没有本地独有的提交），所以删掉重克隆就恢复了。
> **教训**：做这种镜像同步之前先 `git ls-remote` —— 否则删掉 `.git` 就等于丢掉没推的历史。

### ⚠️⚠️ 更严重的一个：仓库里的 `.bat` 是 LF，别人 clone 下来全用不了

**用户反馈**：「检查环境.bat / 一键部署.bat / start.bat 都用不了」。

**根因**：仓库里存的 `.bat` **全是 LF 换行**，而且当时没有 `.gitattributes`。
cmd.exe 不认 LF —— LF 版 `.bat` 会以各种离奇方式炸掉。

复现方式（`core.autocrlf=false` 克隆之后直接跑）：

```
检查环境.bat  →  '&& was unexpected at this time.'
                 '??，实测就踩到了。' is not recognized as an internal or external command
一键部署.bat  →  'The syntax of the command is incorrect.'
start.bat     →  'The system cannot find the path specified.'
```

**三个脚本全废，和用户描述完全一致。**

**为什么本机测不出来**：开发机上 `core.autocrlf=true`，checkout 时会自动把 LF 转成 CRLF，
所以本地双击一切正常 —— **只有别人 clone 下来才会踩到**。这类问题不能靠"我这能跑"来判断。

**修法**：新增 `.gitattributes`

```
*.bat -text
*.cmd -text
```

用 `-text` 关掉一切换行转换，让**仓库里保存的字节就是 CRLF**。
这样不管对方的 `core.autocrlf` 是 `true` / `false` / `input`，甚至不用 git 直接下 ZIP，
拿到的都是 CRLF。（只写 `text eol=crlf` 也能在 checkout 时转，但仓库里仍是 LF，
下 ZIP 仍有风险，所以这里选 `-text`。）

改完要 `git add --renormalize .` —— 否则 git 以为"内容没变"、跳过重新入库，
仓库里存的还是 LF（实测：直接 `git add` 只有真正改过的那一个文件被重新入库）。

**验证**（就是上面那套失败条件，改完之后）：

```
autocrlf=false 克隆 → 六个 .bat 全部 CRLF ✅
检查环境.bat       → 正常跑完，正确报出「还没有 venv / 依赖没装齐 / 没有高德 Key」并给出怎么补
start.bat          → 见下（这条是改完之后又发现的一个问题）
```

## 交通费为什么虚高（已修）

用户反馈：「杭州到上海会默认从杭州打车去上海，导致预算虚高」。
查下来**不是一个 bug，是四层叠在一起**，每层都能单独把预算推高。都是实测出来的。

### 四层根因

**① `_transport()` 只要超过 1.5km 就一律按「打车」计费**

原代码取的是高德驾车路线里的 `route.taxi_cost`（**打车费**）：

```python
if dist < 1.5:
    return TransportToNext(mode="步行", ...)      # 走路
# 其余全部走这里
cost = float(route.get("taxi_cost") or 0)          # ← 打车费
return TransportToNext(mode="打车", cost=cost)
```

于是 40 公里的跨区移动也是打车、城际也是打车。实测上海会出现
「从松江广富林打车 40 公里回人民广场吃饭」，**那一段就是 138 元**。

**② 餐厅按天轮换，完全不看位置**

```python
def _pick(self, restaurants, i):
    return restaurants[i % len(restaurants)]   # 只按天数轮换
```

同一天的餐厅和景点可以相隔 40 公里 —— 上面那 138 元就是这么来的。

**③ 景点按相关度切片，没有地理聚类**

```python
day_pois = selected[i * per_day : (i + 1) * per_day]   # 直接按个数切
```

`selected` 是高德的相关度顺序，于是一天之内可能横跨 40 公里
（实测：松江广富林 + 市中心城隍庙同一天）。

**④ 往返大交通是拍脑袋的固定值，而且完全无视「出发地」**

```python
if pref.transportation == "高铁": return 150 * people * 2    # 固定 150/人
if pref.transportation == "飞机": return 500 * people * 2
```

- 杭州→上海（170km）和杭州→乌鲁木齐（3900km）**估出来一模一样**
- **同城游也照收 600 元"往返高铁"**（实测：杭州市内 2 天 2 人，交通分项 830
  = 接驳 230 + 凭空多出来的往返 600）
- `origin`（出发地）在表单里让用户填，**后端从来没读过它**（全项目搜 `origin`
  只有字段定义和一句提示词）

### 改了什么

| # | 改动 | 位置 |
| --- | --- | --- |
| 1 | 接驳**按距离分档**：<1.5km 步行 / ≤12km 地铁（按人 2~8 元）/ ≤60km 打车（高德真实出租车费）/ **>60km 城际**（不打车，按高铁价） | `_transport()` |
| 2 | 餐厅**就近选**（锚在当天景点的地理中心），且**午餐锚上午那半、晚餐锚下午那半** | `_pick()` |
| 3 | 景点先**最近邻排序**再按天切片 —— 每天变成一条地理连贯的路线 | `_nearest_neighbour_order()` |
| 4 | 往返大交通按**出发地→目的地的实际距离**算（给高德客户端新增了 `geocode()`）；**同城 → 0**；拿不到距离才回退旧固定值 | `_round_trip()` / `AmapClient.geocode()` |
| 5 | 出发地是选填 —— 没填时在方案里**明确提示**这个数是怎么估的 | `OutputGuardSkill._round_trip_note()` |

### 还剩一处**不是计费问题**的（已告知，未改）

上海方案里仍可能看到一段 32 公里的打车（135~138 元）。那是**真实成本**：

覆盖的点），那是行程质量问题、不是计费公式问题，留待下一步。

## 重新构建并更新工作台

改了 `HikiTravel/frontend/src/` 之后（比如改表单字段、改方案视图）：

```bat
cd HikiTravel\frontend
node node_modules\vite\bin\vite.js build --config vite.embed.config.ts
copy /Y dist-embed\planner-embed.js  ..\HikiTravel-AIRI-1.3\public\
copy /Y dist-embed\style.css         ..\HikiTravel-AIRI-1.3\public\planner-embed.css
rmdir /S /Q dist-embed
```

四个关键点：

- 用的是 `vite.embed.config.ts`（**嵌入专用配置**），不是默认的 `vite.config.ts`。
  它按 lib 模式出 IIFE，全局名 `WenlvPlanner`，外壳调 `WenlvPlanner.mount('#wenlv-planner')`。
- **`define: { 'process.env.NODE_ENV': '"production"' }` 不能省**。
  Vite 在 lib 模式下不会自动替换它，而 React/antd 都要读 —— 少了这行，
  产物一加载就抛 `process is not defined`，整个工作台挂不上去。
- 用 `node node_modules\vite\bin\vite.js` 而不是 `npx vite`：这台机器上
  `npx vite` 会报 `could not determine executable to run`。
- 改完外壳的 `public/planner-embed.js` 直接生效，不用重启后端（静态文件按请求读盘）；
  但浏览器可能要强刷一次（Ctrl+F5）绕过缓存。

要重新构建组员原本那个独立整页应用（`frontend/dist/`），仍用默认的
`vite.config.ts`，两者互不影响。
