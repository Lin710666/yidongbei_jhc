# 文旅智能辅助 · 融合版（HikiTravel 后端 + AIRI 网页界面）

赛题 **JBGS-2026-06**（发榜方：杭州网易智企）的比赛工程。

这个目录把两条线并成了一个可运行的产品：

| 来源 | 提供什么 | 在本目录的位置 |
| --- | --- | --- |
| **HikiTravel**（组员重写的后端） | FastAPI 服务、四段式 Skill 流水线（意图 → 异常拦截 → 高德检索 → 规划）、高德实时数据、SQLite 计划库、本地 RAG | `backend/` |
| **5.0 的 AIRI 网页界面** | 外壳：Live2D 虚拟导览员 + 可点击词云 + 全屏结果卡 + 定位导航页 + 营销素材 | `public/`（纯静态，**没有构建步骤**） |
| **HikiTravel 的 React 工作台**（组员新做的） | 「文旅」面板里的行程规划界面：14 字段偏好表单 + 一句话对话生成 + 方案视图 + 实时地图 | `public/planner-embed.js` + `planner-embed.css`（由 `frontend/` 构建而来） |

中间的翻译层是 `backend/app/routers/ui_compat.py`：5.0 的界面原本对着 5.0 那套
Node 后端说话，一共要 60 多个接口；后端换成 FastAPI 之后两边对不上，这一层负责把请求翻译过去、
把结果翻译回来。

## 快速开始

### 一键（推荐）

1. 双击 `install.bat` —— 建虚拟环境、装后端依赖、生成 `backend\.env` 模板
2. 按提示把高德 Key 填进 `backend\.env` 的 `AMAP_API_KEY`
3. 双击 `start.bat` —— 起服务并自动打开浏览器

浏览器打开 <http://localhost:8000>。

### 手动

```bat
cd backend
.venv\Scripts\python.exe -m uvicorn app.main:app --host 127.0.0.1 --port 8000
```

### 依赖

- **Python 3.10+**
- **Ollama**（本机推理，默认 `http://localhost:11434`，对话模型 `qwen2.5:7b`，
  embedding 用 `nomic-embed-text`）—— 全部离线、零成本
- **高德开放平台 Web 服务 Key**（POI / 天气 / 路线，免费申请：
  <https://console.amap.com/dev/key/app>）

三个前端接口用不到 Ollama 也能开：页面能打开、词云能点、目录类接口正常，
只有真正生成方案时才会用到模型。

### 为什么 `.bat` 里要写 `PYTHONUTF8=1`

`pip install -e .` 写出的 `.pth` 文件里，路径是 UTF-8；而 `site.py` 读 `.pth`
时用的是系统区域代码页（中文 Windows 上是 GBK）。本项目所在路径含中文
（`移动杯项目`），于是 venv 里的 python 会在 `init_import_site` 阶段直接
fatal error，报的还是 `UnicodeDecodeError: 'gbk' codec can't decode ...`，
压根不提路径，看起来像 Python 装坏了。

`set "PYTHONUTF8=1"` 解决这个问题。**引号不能省** —— 写成
`set PYTHONUTF8=1 && ...` 会给值尾加一个空格，python 会以
`invalid PYTHONUTF8 environment variable value` 拒绝启动。

## 融合时做的几个关键决定

### 1. `/api/chat` 归原生所有，5.0 界面的 SSE 挂在 `/api/chat/stream`

两边都要「对话」，但协议不同，一个路径没法同时满足：

- **HikiTravel 原生**（组员的 React 工作台在调）一次性返回一整份 `TravelPlan` JSON
- **5.0 的 AIRI 界面**用 SSE 流式解析器读（`public/js/util.js` 的 `sse()`）

所以 `/api/chat` 保持原生 JSON 语义，5.0 那条改成 `/api/chat/stream`（界面里
`public/js/app.js` 对应改了一行）。这样两套前端各拿各的，谁都不用迁就谁。

中间试过一个捷径：让兼容层先注册、把 `/api/chat` 抢下来，原生的挪到
`/api/chat/plan`。能跑，但代价是**组员的 React 界面调 `/api/chat` 会拿到 SSE**，
对话生成直接坏掉。路径不重叠才是干净的解法。

### 2. 「文旅」面板里装的是组员的 React 工作台（整套，原生挂载）

按需求「保留 AIRI 外壳，把组员那套**整套**放进文旅面板」做的。
做法是**把 React 组件直接挂进外壳的 DOM**，而不是套一个 iframe：

- 给组员的工程**新增**了一个嵌入入口（不动他原有代码）：
  `src/embed.tsx` + `src/embed.css` + `vite.embed.config.ts`
- 用 `vite build --config vite.embed.config.ts` 打成 IIFE + 单 CSS，
  产物是 `public/planner-embed.js` 与 `public/planner-embed.css`
- 外壳里就是一个 `<div id="wenlv-planner">`，由 `app.js` 的 `bindPlanner()`
  调 `window.WenlvPlanner.mount('#wenlv-planner')`

**为什么先试了 iframe、又改回原生挂载**：iframe 里是另一个文档、另一套 body 样式，
字体/背景/配色都继承不到外壳，看起来永远是「两块拼在一起的板子」。
同一个文档里挂载才能共用外壳的字体与背景。

**没有全屏按钮**。一开始做过一个「⤢ 全屏」，按需求去掉了：工作台就该老老实实待在
面板里，不该再多一个需要用户理解的交互。（顺带说明一个当时的坑：`backdrop-filter`
会让元素成为 `fixed` 后代的包含块，所以那个全屏当时只能靠改 `.side` 实现。）

**贴合是怎么做到的**——三件事：

1. `ConfigProvider` 切 `darkAlgorithm`（原来的 antd 是浅色白卡，放进深色外壳里非常刺眼）
2. 主色取外壳 CSS 里给「文旅」语义留的那个青绿 `--wenlv`
   = `oklch(76% 0.11 178)` = **#54c8b1**，其余 token 照外壳的
   `--surface` / `--border` / `--text` 对齐（卡片底色 `rgba(255,255,255,.035)`、
   边框 `.08`，实测与外壳同源）
3. 嵌入入口**不导入** `antd/dist/reset.css`，也不导入它的 `index.css` ——
   那两个会改 body / `#root` / `h1~h6` 的全局样式，会和外壳的设计系统打架

**踩过的三个坑**：

- **`process is not defined`**：Vite 在 lib 模式（IIFE）下**不会**自动替换
  `process.env.NODE_ENV`（它假设由使用者提供），而 React 与 antd 都要读它。
  不 `define` 的话产物一加载就抛错、工作台整个挂不上去，而页面本身不报错，
  很容易误判成「没渲染出来」。产物也因此从 1.34 MB 降到 957 KB。
- **antd 的响应式断点按视口算，不按容器算**：`<Col xs={24} lg={8}>` 走的是
  CSS 媒体查询。嵌进 518px 的面板后视口仍是 1600px，于是 `lg` 命中，
  两列被压成 167px / 335px —— 表单挤成一条，比不响应还糟。（用 iframe 时没这问题，
  因为 iframe 有自己的视口，正好 518px。）改用**容器查询**后，面板多窄都自动单列。
- **antd 的 `Row gutter` 是负外边距**：`gutter=16` 时 Row 左右各 `-8px`。整页版里
  外层 padding 会抵消它，嵌进面板后外层 padding 被收成 0，这 8px 就顶出去了
  （实测容器 494 / 可视 486，横向出现滚动条）。把负边距归零即可。
- **`antd` 的 `Button` 会自动给两个中文字符加空格**：「导航」渲染出来是「导 航」。
  写断言时先去掉空白再比，否则会把已经实现的功能误报成缺失（这个我确实误报了一次）。

#### 深色化：把写死的浅色换成主题 token

组员那份 `PlanView.tsx` / `MapView.tsx` 里有几处**内联样式写死的浅色**，
自己是浅色主题时没问题，嵌进深色外壳后就是一块块白的：

| 位置 | 原来是 | 现在 |
| --- | --- | --- |
| 「换一个 / 换一家餐厅 / 选这家」的展开面板 | `#fafafa` | `token.colorFillQuaternary` |
| 实时天气预报的每一天 | `#f5f5f5` | `token.colorFillTertiary` |
| 当晚住宿那块浅绿底 | `#f6ffed` + `#b7eb8f` | `token.colorSuccessBg` + `colorSuccessBorder` |
| 地图示意图（本地画的 SVG） | `#eef3f7` + 文字 `#333` | `token.colorFillQuaternary` + `token.colorText` |
| 次要文字 `#888` / `#555` / `#999` | 写死灰 | `colorTextTertiary` / `colorTextSecondary` |
| 交通行、换一个按钮 `#1677ff` | 写死蓝 | `token.colorPrimary` |

为什么不用外部 CSS 覆盖：这些是**内联样式**，优先级高于任何样式表，
从外面压只能靠 `!important` 硬顶，太脆。换成 token 之后两个主题都对：
`colorFillQuaternary` 在浅色主题下取到的就≈`#fafafa`（他自己的界面观感不变），
`darkAlgorithm` 下自动变暗，谁都不用为对方写特例。

验收方式是"扫整棵 DOM，看还有没有**不透明的近白色背景**"——
判据刻意不是"背景必须是暗的"，因为 token 给的多是低透明度叠色
（`rgba(255,255,255,.04)` 的 rgb 是白的，叠在深底上依然是深色，那不算问题）。

```
方案生成后，把所有展开面板都点开再扫：
  检查了 17 个元素   → ✅ 不透明近白背景 0 个
  卡片底色 rgba(255,255,255,.035) / 边框 .08
  天气格   rgba(255,255,255,.08)  / 边框 .07
  外壳 body 底色 rgb(18,18,18)
```

**原版那套表单去哪了**：界面上不再展示（按需求「之前那个也不要了」），
但**元素仍然留在 DOM 里、只是 `hidden`** —— `app.js` 里大量绑定依赖这些 id
（词云点条件会回填表单、「生成 / 导出 / 朗读」按钮都挂在这些元素上），
删掉会直接报错。只有「生成结果」那个展示位留在外面可见，
词云点「营销文案 / 个性化方案」写结果前会自动把它显出来，避免结果写进看不见的地方。

### 3. 聊天框两条路径都实现了

5.0 的界面会二选一（`app.js:1163`）：开了联网、或当前形象能指挥动作时走
`/api/agent`，否则走 `/api/chat/stream`。实测在这台机器上界面走的是 `/api/agent`。
两条都挂在同一个生成器上——少挂一条，用户就会看到 404。

### 4. 对话时把「词云上点过的条件」一起提交

组员的后端有一条既定的合并契约（`orchestrator._merge_base`）：
**结构化字段优先，对话只补缺**。他们的 React 工作台就是这么用的
（表单已填字段作为 `base` 提交）。

5.0 的聊天框原来什么都没带，于是完全依赖 LLM 意图解析 —— 而那个解析器对
中文数字不敏感（「两天 / 两个人」都认不出）。这里把 5.0 侧也接到同一条契约上：

- 取 `cloud.getSelected()`，也就是**用户真的在词云上点过**的词
- 按 capabilities 里这些词的 `payload` 映射成 HikiTravel 的画像字段
- 只有一处例外：天数还要看用户有没有亲手动过天数控件（拖滑杆 / 点箭头），
  动过就以控件当前值为准

**为什么不能直接拿表单值当 `base`**：5.0 的表单里天数默认 2、城市默认杭州，
那是默认值不是用户填的。全送上去的话，用户在聊天框说「帮我排苏州三天」
会被默认值盖成「杭州 2 天」，比不合并还糟。所以只认点过的词。

顺带修掉一个我自己的渲染 bug：方案标题原来写的是
`params.get("city") or "目的地"`，而对话那条路 `params` 是空的，
于是聊天生成的方案标题会变成「**目的地** · 4 天3晚 个性化方案」，像模板没填。
`TravelPlan` 本身没有 `destination` 字段，改成按
「点过的城市 → `summary` 开头的城市名 → 各日 POI 多数决」依次推导，
并去掉高德返回的「市」后缀（杭州市 → 杭州）。

多数决这一步不是多余的：实测一份苏州方案里 Day 1 排的是上海豫园与外滩，
取「第一个 POI 的城市」会把标题写成上海市。

### 5. 结果卡排版是硬契约

`app.js` 的 `layoutResultBlock()` 靠 **H2 标题的文案**决定排版：
`行程总览` / `费用预估` 各占一整行，`## Day N` 那几块横着排成一行，
`版本 A` / `版本 B` 排成两列。所以 `_render_plan_markdown()` 输出标题时
一个字都不能改，否则排版就散了。

### 6. 角色卡用深合并，不用 5.0 的浅合并

5.0 的 `lib/cards.js` 是 `normalize({...patch, ...input}, base)`：patch 里带了
`voice` 键，整个 `voice` 对象就被替换，缺失字段回退到**默认值**而不是原值。
后果是只发 `{voice:{speaker:'vivian'}}` 时，`voice.instruct` 会被清空——
用户挑完音色，刚写的语气描述就没了。

`cards_store.py` 改成递归深合并：patch 里出现的字段才覆盖，明确传 `null`
仍然能清空。表达力没变弱，只是不会误删。

### 7. 没接入的可选功能，统一返回 501 + 一句人话

全景图、图片转 3D、Blender 联动、视频背景、我的音色、语音识别（STT）
和语音合成（TTS）都是 5.0 的独立服务，融合版没有带过来。这些路径在 5.0 里
存在、前端也照样会调，缺了就返回 404 —— 用户看到裸的 `HTTP 404`，
分不清「这个功能本来就没有」还是「程序坏了」。所以显式声明 501 并写清原因，
前端 `api()` 会把这段文案原样弹出来。

### 8. 前端资源自动带版本号，改了就必然失效

`StaticFiles` 只发 `Last-Modified` / `ETag`，**不发 `Cache-Control`**，
浏览器于是按「启发式缓存」自己算一个新鲜期（常见做法是文件年龄的 10%），
在那段时间里直接吃本地副本、连问都不问服务器。

改前端的时候这会踩得很惨，而且症状极具误导性：`index.html` 是新版
（所以界面上出现了新按钮），而**同一次改动里的 `app.js` 还命中旧缓存** ——
页面就成了「按钮在、点了没反应、面板一片空白」。改的人只会以为代码写错了，
其实服务器上的文件完全是对的。（这个我真被绕进去过一次，还是看主人的截图才发现的 ——
我只用无头浏览器自测，无头每次都是全新会话、永远命中不到缓存，所以永远测不出来。）

做了两层防护：

**① `main.py` 加中间件**，对**非 `/api` 路径**一律加
`Cache-Control: no-cache, must-revalidate` —— 浏览器每次都带 ETag 回来问一次，
没变就 304，变了就拿新的。`/api/tile` 的瓦片缓存（`max-age=86400`）不受影响。

**② 首页的资源 URL 带版本号**（这层才是真正兜底的）。
`index.html` 里自己的 css/js 都写成 `?v=__ASSET_V__`，
`main.py` 的 `index_html()` 在每次返回首页时，用 **`public/` 下最新的文件修改时间**
替换掉这个占位。任何前端文件一改，所有资源 URL 立刻变化 → 缓存必然命中不了。

```
改动前  /js/app.js?v=1789837582
改一下 app.js 后（不改任何配置）
        /js/app.js?v=1789837785   ← 自动变了
```

所以**不需要任何人手动清缓存、也不需要手动维护版本号**。`vendor/` 下的
第三方库不加版本号（体积大又不会变，没必要每次重下）。

顺带一条工程教训：**面板不允许"一声不响地空白"**。空白的容器既可能是"还在加载"、
也可能是"脚本没到"、也可能是"React 渲染崩了"，三种情况长得一模一样，
排查成本极高。现在：

- `#wenlv-planner` 里写死了「正在载入行程规划工作台…」，挂载成功才被 React 顶掉
- 脚本标签带 `onerror`，把加载失败记下来
- `mount()` 外面包 try/catch，渲染期抛错另外用 `window.onerror` 接
- React 里加了 ErrorBoundary（渲染期的错不会被 try/catch 接住）
- 每条失败路径都把**具体原因写进面板**，而不是留在 console 里

### 9. 词云点选的条件同步进工作台（外壳与工作台之间的桥）

「文旅」面板换成组员的工作台之后，词云就成了"半截"的界面：它原来把点选的
**目的地 / 预算 / 同行人群 / 兴趣 / 饮食禁忌**填进右侧面板的表单，
而那张表已经被 `hidden` 收起来了。实测确认：

```
点「杭州 / 舒适 / 亲子 / 美食」
```

### 启动耗时：修掉一个导入期的 42 秒

1. 索引改成**首次 `search()` 时才建**（懒加载）—— 导入立刻降到毫秒级
2. embedding 换 **批量** `/api/embed`，往返次数从 N 次降到 1 次
3. 两个路由共用同一个 `get_orchestrator()` 实例

```
改前  import app.main          42.10s
改后  import app.main           0.51s      （82 倍）
首次 search（建索引一次）        6.16s
第二次 search（走缓存）          2.09s
```

### 对话里的「两天 / 两个人」解析不出来（组员的解析器，未改）

这个会直接被评委看见，所以放最前面。输入
**「帮我规划杭州两天，两个人，喜欢人文历史」**：

| 字段 | 期望 | 实际 |
| --- | --- | --- |
| 天数 | 2 | **1** ❌ |
| 人数 | 2 | **1** ❌ |
| 目的地 | 杭州 | 杭州 ✅ |
| 兴趣 | 人文历史 | 人文历史 ✅ |

实测稳定复现（连跑两次结果一致，不是随机），而且**两条解析路径都有这个盲点**：

- **LLM 抽取路径**（首选，`intent_skill.py` 的 `chat_json`）：目的地和兴趣都抽对了，
  唯独漏掉天数与人数 —— 说明是提示词/字段说明的问题，不是模型不行
- **规则兜底路径**（`_rule_parse`）：
  - 天数用的是 `r"(\d+)\s*天"`，**只认阿拉伯数字**。`两天` / `三日游` / `玩三天`
    全部匹配不到（`2天` 能匹配）
  - 人数用的是 `r"(\d+)\s*人"` 加一张关键词表 `情侣|夫妻|两口子|二人|两人|双人`
    —— **「两个人」不在表里**，同样漏掉

中文里「两天两晚」「三个人」是最自然的说法，所以这个盲区影响面很大。
修法不复杂（正则加中文数字映射 + 提示词里明确「中文数字也要转」），
但这属于组员的 intent skill，**按主人的意思没有去动它**，改成在融合层做适配
（见「关键决定 4」）：界面上点过的条件会作为结构化字段提交并优先于解析结果，
所以**走词云/表单那条主路径不受影响**；只有「纯在聊天框里打中文数字」才会露出来。

## 高德 Key 的处理

`install.bat` **故意不硬编码** Key，只生成一个空模板。

原因：写进公开仓库的 Key 会被爬走，每日配额提前耗光 —— 而这正好会发生在
演示当天。请自己申请一个免费 Key 填进 `backend\.env`（这个文件已 gitignore）。

## 重新构建并更新工作台

改了 `HikiTravel/frontend/src/` 之后（比如改表单字段、改方案视图）：

```bat
cd HikiTravel\frontend
node node_modules\vite\bin\vite.js build --config vite.embed.config.ts
copy /Y dist-embed\planner-embed.js  ..\HikiTravel-AIRI\public\
copy /Y dist-embed\style.css         ..\HikiTravel-AIRI\public\planner-embed.css
rmdir /S /Q dist-embed
```

四个关键点：

- 用的是 `vite.embed.config.ts`（**嵌入专用配置**），不是默认的 `vite.config.ts`。
  它按 lib 模式出 IIFE，全局名 `WenlvPlanner`，外壳调 `WenlvPlanner.mount('#wenlv-planner')`。
- **`define: { 'process.env.NODE_ENV': '"production"' }` 不能省**。
  Vite 在 lib 模式下不会自动替换它，而 React/antd 都要读 —— 少了这行，
  产物一加载就抛 `process is not defined`，整个工作台挂不上去。
- 用 `node node_modules\vite\bin\vite.js` 而不是 `npx vite`：这台机器上
  `npx vite` 会报 `could not determine executable to run`。
- 改完外壳的 `public/planner-embed.js` 直接生效，不用重启后端（静态文件按请求读盘）；
  但浏览器可能要强刷一次（Ctrl+F5）绕过缓存。

要重新构建组员原本那个独立整页应用（`frontend/dist/`），仍用默认的
`vite.config.ts`，两者互不影响。
