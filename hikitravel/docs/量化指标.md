# 量化指标

> 用于答辩演示与文档中说明成果。区分「可实测」与「预期（需上线验证）」，
> 请如实标注，避免夸大。

## 一、可实测的性能指标

| 指标 | 目标值 | 测量方式 |
|------|--------|----------|
| 整单生成耗时（3 天行程，本地 7B/CPU） | 实测约 100~110 秒（未预热的首次约 141 秒） | 本机实测（Ryzen 7 8845H，Ollama 100% CPU）：检索 7s、规划 24~60s、体检 59~75s。体检最耗时，且内部可能触发一次整体重排 |
| 启动预热 | 后台约 62s（冷），**不阻塞服务可用** | 加载模型 + 预填 4 段系统提示词（约 2200 token 的预填充提前付掉）。Ollama 缓存按前缀命中，实测同一提示词换用户输入预填充 19.0s → 0.7s。`OLLAMA_PREWARM=0` 可关 |
| 行程首屏可见 | 实测 35s（整单 89s） | SSE 流式生成：规划环节结束即发行程初稿并可渲染，体检继续在后台跑完再补结论 |
| 生成过程可见 | 每个环节实时显示 | 环节开始/结束 + 实际耗时（检索 7s、安排行程 28s、规划体检 54s）；触发重排时也会显示"按体检结论重排行程" |
| 体检失败兜底 | 不作废行程 | 体检属附加质量报告：失败时如实写入"体检未能完成"，行程保持完整可用（原先会让整单返回 502） |
| 规划耗时（已优化） | 实测 24~60 秒（方差较大） | 大模型只输出"去哪些景点"的扁平清单，分天/排线交给代码；生成长度随候选池波动 |
| 回退优化 | 单段 ≤ 25 公里、当天 ≤ 40 公里由代码判定，秒级 | 路线体检与最近邻重排均为纯计算 |
| 天气/POI 数据获取 | 依赖高德 API，命中缓存后 < 1 秒 | 接口耗时（进程内缓存，省掉重复调用与限流等待） |
| 生成中可打断 | 支持取消 / 重试 / 连接自检 | 前端 AbortController + /api/health |
| 前端首屏渲染 | < 3 秒 | 打包后静态资源体积 |

## 二、可用演示呈现的指标

| 指标 | 数值 | 说明 |
|------|------|------|
| 必填字段 | 4 项 | 目的地 / 天数 / 同行人数 / 总预算；缺哪项就明确提示补哪项，不用静默默认值。兴趣导向不必填——留空表示「未指定」，由系统按全部类别检索，而不是替用户认领一个他没提过的兴趣 |
| 行程约束提示 | 1 类（查后） | 同行有老人 + 选中景点含爬坡类（在选点之后判，才有判断依据）。原「需求矛盾检测」Skill 已删除：它是硬编码规则、只覆盖几条窄场景，而"采纳"要重跑整单，性价比低 |
| 规划体检维度 | 代码 4 类 + 语义 3 类 | **代码判**：路线顺序优化、长距段 / 异常绕行、折返、预算对账、必去漏排 / 重复 / 时间重叠的证伪；**模型判**（只审这三类语义问题）：①点位到底是不是个景点 ②有没有跟用户原话冲突 ③有没有偏离用户填的兴趣。实测让 7B 把七项都审一遍，它主要在复述代码结论，还会编出"必去景点没排进去"这种与事实相反的结论 |
| 绕行判据 | 跟本趟基线比 | 阈值 = max(1.5 倍, 本趟绕行系数 × 1.25)，且实际比直线多跑 ≥3 公里才报。平潭实测系数 2.15、岛上每段路都在绕，写死 1.5 倍等于天天报警。实测同一份规划：4 条绕行播报 → 只剩 1 条真正异常的（绕 3.1 倍、多跑 4.2 公里） |
| 折返判据 | 只看景点之间 | 吃饭、回酒店插在中间天然多跑几公里，那是行程不是路线问题。阈值由 3 公里提到 5 公里。实测那份规划里 1 条"折返"播报消失 |
| 预算对账 | 确定性，一行减法 | 估算总花费 vs 用户填的预算，超了直接点名。实测杭州 3 天：估算 3892 元 / 用户填 2000 元，之前体检一个字都没提；现在明确写出"超出 1892 元（95%）"并给改法 |
| 用户原话进体检 | 对话模式才有 | 画像字段装不下的诉求（"不想爬山""带老人"）只有原话里有；排斥项删掉之后这是它们唯一的入口。体检 payload 里带上「用户原话」，让审稿人对照行程挑冲突 |
| 路线优化 | 确定性 | 按真实坐标算每天总距离、折返、超长单段；最近邻重排 + 2-opt 局部优化当天景点（秒级，可复现） |
| 体检后重生成 | ≤ 1 次 | 仅"硬伤"未解决时触发，带体检结论重排；新版更差则保留原版 |
| 推荐排序综合分 | 3 套 | 景点＝热度×0.6＋评分×0.4（**不含距离**：距离是"路线"的事，统一归规划阶段）；餐厅＝先取"链上该位置附近"的前 5 家 **＋ 最多 3 家"比最近候选多绕 6 公里以内"的本地特色店**，再按距前后节点×权重＋评分×权重＋本地特色 0.18 − 连锁快餐 0.30；**酒店＝评分×权重＋距「切点两侧的真实景点」×权重**（切点＝当晚住哪，两侧正是「今天玩完回酒店」和「明早从这里出发」两段，可查真实路线） |
| 节奏与耗时 | 3 档 | 悠闲 2.5h/景点、适中 1.8h、特种兵 1.2h；每餐 1.5/1.2/1.0h。原来耗时是固定 2.5h，导致「特种兵」一天 4 个景点 = 10h + 两餐 3h 必然超时，第 4 个景点被砍——**特种兵和适中实际没差别** |
| 饮食禁忌 | 只留判得准的 | 「无海鲜／海鲜过敏／清真」按店名硬排除。实测在 91 家真实餐厅上，「无海鲜」排掉的 25 家全是真海鲜店，零误判。原「排斥项」（爬山等）已**从画像字段、意图抽取、体检提示词、前端表单四处一起删除**：判据不可靠（浙江省博物馆(孤山馆区)、巍山古城、雷峰塔景区都被误判成"爬山"），**用错判据自动改用户行程比不做更糟** |
| 用上高德原有字段 | 3 个 | ①`biz_ext.open_time`（25/25 家餐厅有）→ 排餐时校验营业时间，实测曾把晚餐排在 17:30、而那家店 10:30-17:30 已关门；②`keytag`+`atag` 招牌菜标签（19/20 有）→ 统计出本地特色词（平潭 = 大排档/海鲜），给本地店加分，实测 5/20 份规划曾把麦当劳/肯德基排进行程；③`type` 第三级 → 菜系（海鲜酒楼/潮州菜） |
| 内容优先选餐 | 2 类餐厅 | 大模型从"餐厅候选"里挑出**值得专门去吃**的店（最多 = 天数），系统优先把它们排进行程，并**不参与随后的距离微调**——实测踩过：内容店刚排进去就被"省 0.3 公里"换成景点门口的连锁快餐。两道绕路上限：①离链上前后任一站 ≤ **15 公里**；②比"就近能吃的备选"最多多绕 **6 公里**。上限②是同一个额度（`MEAL_CONTENT_EXTRA_KM`），也用来管"本地特色店能不能进候选池"和"最后比价时哪些候选还算数"——口径统一，避免"加分能值七八公里" |
| 连锁餐饮降权 | −0.30（只降权不排除） | 命中品牌词（麦当劳/肯德基/蜜雪冰城…）或通用餐饮词（快餐/汉堡/咖啡/饮品）时降权，**但本地特色命中即豁免**（避免误杀"潭式煎包"这类本地小吃）。本地特色加分还带 4.0 分口碑门槛：实测不加门槛时，0.18 的加成会把 3.6 分的店推上 4.5 分的店 |
| 内容额度的实测效果 | 第 1 天最长单段 10.1 公里 → 4.0 公里 | 同一输入（平潭 3 天 / 必去长江澳 / 适中）反复跑真实全链路：那顿午饭从「镜沙 → 陈记（10.1 公里）」变成「镜沙 → Sea U 云顶海景餐厅（3.2 公里）→ 北港村（4.0 公里）」；6 顿正餐全是本地馆子，0 家连锁快餐、0 家咖啡店；点名店「海先生大排档」仍排进第 3 天，卡片上带着模型给的理由 |
| 国家级景区名录 | 256 条（本地查表，零调用） | `app/data/authority.json`，来自维基百科「国家5A级旅游景区」条目（演示种子，完整名单应以文旅部公告为准）。命中即标注「国家级5A景区」并给一点排序倾斜。实测：杭州西湖风景名胜区 → 命中；灵隐寺 → 不命中（正确，它不是 5A） |
| 实时攻略检索 | 可选，默认关闭 | 接公开搜索 API 做"搜索 + 阅读"（参考 DeepSeek 联网搜索的做法：搜索 + 阅读 + 带引用）。**四条底线**：默认关闭；查询只带城市名不带画像；摘要只作偏好提示、实体必须能在高德找到；失败只记日志、不影响生成 |
| 餐厅微调口径 | 距离 + 口碑 + 内容 | 先排除绕路超过 0.3 公里的候选，再在剩下的里比综合分（不会为省 10 米换掉一家高分餐厅）；"值得专门去吃"的店直接跳过这一步 |
| 体检误报过滤（必去覆盖） | 名字互相包含 | 用户写"长江澳"、行程里用的是景点库正式名"平潭国际旅游岛·长江澳"时，模型会误报"必去景点未出现在行程中"。这类与规划事实矛盾的结论按"名字互相包含"证伪后丢弃（实测平潭那份规划命中） |
| 作息规则 | 3 条 | 非特种兵不早于 8:00 出发；午餐不晚于 14:00；晚餐不早于 17:30（超时优先砍景点，不砍晚餐） |
| 预算口径透明 | 2 条 | 往返大交通为估算值（实际购票为准）；门票价缺失时明确说明按 0 元计 |
| 必去景点定位 | 2 条路径 | 下拉选定 = 带 adcode/坐标，直接用坐标；手输 = 按名字解析，解析不到会点名提示，不静默留空点 |
| 行程实拍图 | 每个卡片 1~3 张 | 景点/餐厅/酒店卡片展示高德 POI 实拍图，已统一 https；加载失败自动隐藏，不留空位 |
| 必去景点的图与评分 | 修掉"没有图片" | 根因两处：①目的地下拉给的 adcode 可能落成**区级**（实测「杭州市 + 330102 上城区」），旧逻辑把它当检索范围，整趟行程被缩进上城区；②必去景点若在别的区（「青山湖景区」在临安），区县范围内搜不到真实记录 → 退化成**只有坐标、没有图也没有评分**的占位点。修法：目的地名与父级城市一致时按**城市范围**检索（用户明确选了区则照旧保留区级）；区县范围搜不到时再用父级城市试一次。实测复现原偏好：必去「青山湖景区」现在带 3 张实拍图、评分 4.8 |
| 非景点场所过滤 | 影城 / 剧院 / 文体中心 / 体育馆 | 逐条核对高德分类码：「西航国际影城」= **080601 电影院**、「西湖区文体中心」= **140800 文化宫**、「运河大剧院」= 080603 剧场——它们是靠兴趣分类码被"推荐"成景点的（前者还排进了平潭那份规划的第 2 天）。两层修：①把 `080600 影剧院`、`140800 文化宫` 从**兴趣检索**的分类码里去掉（不再主动推荐；用户点名时 `ATTRACTION_TYPES` 里仍保留，照样能解析出照片与评分）；②名字护栏（影城/影院/剧院/剧场/音乐厅/文体中心/体育馆/体育场/游泳馆/健身）把从别处漏网的挡在自动选点之外，并写进体检清单。实测平潭：候选池 23 个里 0 个场馆类，行程不再出现西航国际影城；「湘湖体育公园」这类真公园不误伤 |
| 旧规划补图 | 零网络优先 | 读本地旧规划时补一次图：先用**同一份规划自带的候选池**按名字包含关系补（零网络、不改坐标、不动行程）；还缺的才按名字 + 目的地范围查一次高德，且**只在"名字互为子串"的命中里取离该点坐标最近的那条**（所以不会把南昌青山湖塞给杭州青山湖）。实测两条旧规划：长江澳 → 3 张、青山湖景区 → 3 张 |
| 景点去重 | 实测 9 → 5 | 同一片景区的多条高德记录合并：距离 < 500 米直接合并；名字词干 ≥ 3 字且 < 5 公里也合并（并传递合并）。必去景点受保护，不会被别名挤掉；合并了哪几个写进体检清单 |
| 地域收敛（GeoGate） | 杭州实测 32 → 27 | 高德是按**行政区**给结果的（千岛湖属杭州市淳安县，离西湖 130 公里），而综合分不含距离，于是千岛湖能排到第 4 名、被模型挑中或补足进来。新增 `backend/app/skills/geo_gate.py`：锚点 = **用户必去点 + 候选最密集的一带（10 公里网格）**，阈值 = `clamp(2×距离P75, 15, 60)` 公里，切掉在阈值外的候选并**写进体检清单**（想保留就设为必去）。实测杭州切掉千岛湖 130 / 垂云通天河 69 / 径山寺 42 / 青山湖 37 / 塘栖 29 公里；平潭全市候选都在 20 公里内 → 一个都不切；"市区 + 远郊各一簇且必去点在远郊" → 不切（不替用户砍簇）。前端「换一个」的备选池仍给全量 |
| 必去景点候选 | 按分类码过滤 | 下拉候选改用 place/text + 景点类分类码，排除「自然地名·海湾海峡」（坐标是海湾中心，会画在海里）与停车场；实测「长江澳」返回的全部是风景名胜，自带评分与 3 张实拍图 |
| 距离度量 | 真实驾车优先 | 选中景点之间取真实驾车距离（实测平潭 30 对 ≈ +9 秒）；自动估绕行系数修正直线低估（实测平潭 **2.15**，与人工测量的 1.7~2.7 倍吻合）。全量换真实路线不可行：实测每份规划 12,630 次距离计算 / 5,034 对坐标 |
| 当日路线闭环 | 终点纳入优化 | 一天按「起点 → 景点 → 当晚酒店」优化，实测某日 32.4km → 24.2km。此前只优化前半段，出现过第 2 天 20:13 结束在离酒店 7.8 公里处 |
| 餐厅分配顺序 | 按稀缺度排序 | 先给"离餐厅最远"的那天挑，避免先排的天抢走后排最需要的餐厅（实测：平潭某餐位最合适的两家分别被第 1、3 天先占走，导致只能选 9.3 公里外的一家） |
| 分天方式 | 先串链、再切段 | 把所有景点串成一条链（每个点都当一次起点跑最近邻 + 2-opt，取最短），再用动态规划选切点：先压"最长的一天"，再压不均衡。链的总里程与切点无关，所以优化目标就是"别让某天独自扛大半路程" |
| 选点后的双校验 | 跨度 + 配套 | 成链切天之后，逐天检查两件事：①当天点集跨度是否超过 **15 公里（真实驾车距离口径，≈直线 8 公里）**；②某个景点 5 公里内有没有餐厅（否则会跑很远吃饭）。命中就把"最孤立/最没饭吃"的**非必去**景点换成更合适的候选（要靠近当天其它点、评分不低于原点 0.5 分、还靠近餐厅），最多 2 轮；必去不动、且只按**最终那一版**复算后报告。**这一步是必要的兜底**：实测最近 14 份规划全部触发"补足"（大模型通常只给 5~8 个、容量 9），而补足的旧规则"地理盲" |
| 补足规则 | 先质量、后位置 | 大模型给的点不够时，先在按分数排序的前 6 个候选里圈定，再挑**离已选景点最近**的那个。旧规则是直接取分数最高的（完全不看位置），可能把城市另一端的点塞进来 |
| 跨天衔接 | 结构上天然成立 | 相邻两天只差走过一条边，不再需要"跨天权重"；而且切点正好落在两天之间，酒店选址（当天中心 ↔ 次日中心）天然贴着切点。实测三份真实平潭规划：全天总里程下降 **10~16%**，"北边 3 个点被拆到两天"的问题消失 |
| 去重误判护栏 | 2 类反例 | 地名前缀不误杀（平潭坛南湾 / 平潭北港村，词干只有 2 字不合规）；异地同名不误杀（两个千岛湖湖区，超出距离护栏） |
| 跳转降级层级 | 4 级 | Scheme → 超时检测 → H5 → 复制口令 |
| 雨天备选（Plan B） | 自动替换室内 | 基于实时天气触发 |

## 四、演示建议
