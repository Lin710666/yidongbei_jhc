为什么要经过 `airi-bridge`

1. 协议不一样。AIRI 的语音提供商只认 OpenAI 兼容的 `POST /v1/audio/speech`，
   本机 Qwen TTS 给的却是 `POST /qwenapi/v1/custom-voice`。字段名、音色表示、
   返回格式（base64 JSON 还是二进制）全都对不上，中间得有一层适配。
2. 文旅业务逻辑只在本仓库实现一处，`airi-bridge` 走代理转发而不是复制一份。
   SKILL.md 更新后两套同时生效，单一事实来源就保住了。
3. 跨域也是绕开的。那份交付物的 `serve.js` 把 `/bridge/*` 反代到本机桥，
   页面用同源路径访问，不碰 CORS。

> **V4.1 起这件事已经内置了**（见 2.6）：本项目自己就能提供
> `/v1/chat/completions`、`/v1/audio/speech`、`/wenlv/*`、`/memory/*`、`/cards/*`，
> 并且带 Bearer 鉴权与逐项能力开关。所以现在 AIRI 可以直连本项目，不必再单独跑
> 那份仓库外的 `airi-bridge`。上面这张图描述的是「交付物 ①」当初的接法，保留下来
> 是为了说明那三跳的由来。

### 2.2 视觉语言如何对齐 AIRI

AIRI 用 UnoCSS 的 `presetChromatic`，运行时由 OKLCH 派生整套色板，关键变量是
`--chromatic-hue`（`baseHue: 220.44`）：`primary` 偏移 0、`complementary` 偏移 180、
`tertiary` 偏移 60。本项目在纯 CSS 里复刻了这套机制：

```css
:root {
  --chromatic-hue: 220.44;
  --primary:       color-mix(in srgb, oklch(78% 0.14 var(--chromatic-hue)) 100%, transparent);
  --complementary: color-mix(in srgb, oklch(95% 0.11 calc(var(--chromatic-hue) + 180)) 70%, oklch(50% 0 360));
  --tertiary:      color-mix(in srgb, oklch(95% 0.11 calc(var(--chromatic-hue) + 60)) 70%, oklch(50% 0 360));
  --bg: #121212;                                  /* AIRI 的 theme-color */
  --ease: cubic-bezier(0.16, 1, 0.3, 1);          /* AIRI 的动效曲线 */
}
@property --chromatic-hue { syntax: "<number>"; initial-value: 220.44; inherits: true; }
```

背景的色相漂移动画（`hueDrift`）也来自 AIRI 的 `.dynamic-hue` 做法。
另外角色卡的「主题色」会被换算成色相角写回 `--primary`，
所以换角色卡时，整站主色会一起换掉。

### 2.3 交互词云：布局算法

词云用阿基米德螺线 + 矩形碰撞检测生成：

```
1. 环心留空：rMin = 短边 × 17%   ← 让 Live2D 人物站在中间不被遮住
2. 环外边界：rMax = 短边 × 49%
3. 对每个词，theta 递增、r 线性增长，第一个不与已放置矩形相交的位置就放下
4. 纵向压 0.86 倍，观感更"环绕"而不是"正圆"
5. 字号 = 11px + (权重归一化) × 14px，权重分三档亮度
6. 放不下的词退化为底部行式排布；容器过小时整体退化，不叠字
```

词条数据来自服务端（`lib/wenlv.js` 的 `WORD_CLOUD`），不在前端写死。
每条词带 `action` + `payload`，前端 `handleWordAction` 按 action 分发：

| action | 效果 |
| --- | --- |
| `plan` | 回填表单（城市/天数/预算/人群/兴趣/禁忌）→ 切到文旅页签 → 立即开始流式生成 |
| `marketing` | 回填营销表单 → 立即生成 A/B 双版本文案 |
| `panel` | 切换到六个页签之一（对话 / 文旅 / 外观 / 记忆 / 角色卡 / 声音） |
| `intake` | 触发"信息缺失集中追问"演示 |
| `audit` | 说明输出质检机制 |
| `export` | 把当前结果导出为 Markdown |
| `remember` | 弹层输入一条长期记忆 |
| `vision` | 打开图片选择（配合本机多模态模型） |
| `speak` | 朗读最后一条回复 |
| `expression-cycle` | 轮换 Live2D 表情 |
| `greet` | 角色打招呼 + 播一个动作 |

词云与表单引用同一份选项常量（`OPTIONS` / `DEFAULTS`），
所以两边不会对不上。

### 2.4 Live2D 实现

- 运行时是 `pixi.js@7.4.2` + `pixi-live2d-display@0.4.0`（cubism4 构建）加 Live2D Cubism Core。
  三个文件都已本地化到 `public/vendor/`，离线可用，不依赖任何 CDN。
- 模型放在 `public/models/<名字>/`，一套模型一个目录，目录里需含一个 `.model3.json`。
  仓库不附带模型文件（第三方版权）；双击 tools\ 下的「获取示例模型.bat」会装好三套
  Live2D 官方示例（桃瀬ひより / 春 / Mao），也可以直接用自己的 Cubism 4/5 模型。
- 模型得声明两样东西才动得起来：`model3.json` 的 `Groups` 里要写 `LipSync`（参数
  `ParamMouthOpenY`），`FileReferences.Motions` 里要写动作组。缺了这两项模型照样能显示，
  但不会张嘴、不会做动作，这是模型配置的问题，与渲染器无关。
- 嘴型同步由 TTS 音频驱动。TTS 返回的 wav 交给 WebAudio，用 `AnalyserNode` 取实时频谱能量
  （只取人声主要频段 2~48 bin），再经一阶低通平滑逼近目标值，最后写进 `ParamMouthOpenY`。
  该模型 `model3.json` 的 `Groups` 里正好声明了 `LipSync → ParamMouthOpenY`。
- 视线跟随就是把鼠标位置换算成舞台归一化坐标，调 `model.focus(x, y)`。
- 表情从 `model3.json` 的 `Expressions` 读列表（该模型有 10 个）。

### 2.5 后端结构

`server.js` 是唯一的入口，零第三方依赖（只用 Node 内置模块）：

```
GET  /                          静态页面（SPA 风格，但面包屑只有一层）
GET  /api/status                总状态：Ollama / TTS / 记忆 / 角色卡 / 样本库 / Live2D 模型
GET  /api/capabilities          能力清单：选项 + 词云 + 音色 + 模型
POST /api/chat                  SSE 流式对话（人设 + 记忆召回 + 可选视觉）
POST /api/wenlv/generate        SSE 流式方案/文案/追问（含输出质检）
GET  /api/quick-plan            Agent 友好：纯文本方案
GET  /api/quick-marketing       Agent 友好：纯文本文案
GET/POST/DELETE /api/memory*    机体记忆 CRUD + 检索
POST /api/vision                视觉理解（base64 图片 → 描述）
POST /api/tts                   语音合成（返回 audio/wav 二进制）
GET/POST/PUT/DELETE /api/cards* AI 角色卡 CRUD + 导入 + 导出
GET/PUT /api/providers          外部模型接入配置（密钥回传时打码）
POST /api/providers/models      拉取外部端点真实可用的模型列表
POST /api/providers/test        三级校验：连通性 / 模型名 / 对话探针
GET/PUT /api/openapi            对外开放开关、令牌与能力勾选
POST /v1/chat/completions       入向：OpenAI 兼容对话（流式 / 非流式）
GET  /v1/models                 入向：模型列表
POST /v1/embeddings             入向：文本向量
POST /v1/audio/speech           入向：语音合成（audio/wav）
```

安全与健壮性（对应赛题"异常处理"评分点）：

| 措施 | 实现 |
| --- | --- |
| 目录穿越 | `path.normalize` + 必须带分隔符边界比对（防同前缀兄弟目录） |
| `data/` 不外泄 | `data/` 在静态根目录（`public/`）之外，另有 `public/data` 403 兜底 |
| 畸形 URL（如 `/%`） | `decodeURIComponent` 抛异常 → 400，且服务保持存活 |
| 请求体过大 | 超过 150 MB 返回 413 并 `req.destroy()` |
| 非法 JSON / 非法 type | 400，带 `code` 字段 |
| 图片过大 | 前端先降采样到 1280px；后端再校验 base64 体积，超 12 MB 返回 413 |
| 模型超时 | `AbortSignal.timeout` → 504，并提示"首次调用较慢，可先 `ollama run` 预热" |
| Ollama 未运行 | 502 + 可直接照做的安装/启动命令 |
| 模型未下载 | 503 + 明确的 `ollama pull` 命令 |
| 端口占用 | `EADDRINUSE` → 友好提示 + 换端口建议，不抛难懂的堆栈 |
| 进程级兜底 | `unhandledRejection` / `uncaughtException` 先记日志不退出 |
| 请求体读取失败 | Promise reject → 统一 `fail()` 转成对应状态码 |

### 2.6 外部 API 接入（V4.1 新增，双向）

上面那套默认全本地。V4.1 补上了"外部接入"，两个方向各自独立、默认关闭：

```
                 ┌──────────────────────────────────────────┐
  出向（去调别人）│  lib/providers.js                        │
                 │    · 预设表（19 家，含自定义端点）          │
                 │    · data/providers.json（含 API Key）     │
                 │    · OpenAI 兼容协议：chat/stream/embed/   │
                 │      vision/listModels + 三级校验          │
                 └────────────────┬─────────────────────────┘
                                  │ 按能力分流
                 ┌────────────────▼─────────────────────────┐
                 │  lib/inference.js（路由层）                │
                 │    接口与 lib/ollama.js 完全一致            │
                 └───────┬──────────────────────┬───────────┘
                         ▼                      ▼
              本机 Ollama :11434        外部 OpenAI 兼容端点
              （默认）                   （对话/视觉/向量各自开关）

                 ┌──────────────────────────────────────────┐
  入向（别人调我）│  /v1/chat/completions  /v1/models         │
                 │  /v1/embeddings        /v1/audio/speech   │
                 │  /wenlv/*  /memory/*  /cards/*（别名）     │
                 │  Bearer 鉴权 + 逐项能力开关                │
                 │  配置：data/openapi.json（默认关闭）        │
                 └──────────────────────────────────────────┘
```

**为什么路由层是个"同接口替身"，而不是在每个调用点加 if。**
`createMemory({ ollama })` 和 `createWenlv({ ollama })` 本来就是依赖注入的，
`lib/inference.js` 提供一个接口完全一致的对象替换掉 `ollama` 即可 ——
结果就是 `lib/wenlv.js` 与 `lib/memory.js` **一行都不用改**，路由规则只存在一处。

**为什么视觉与向量要各自独立开关。** 绝大多数外部供应商（DeepSeek、Groq、Kimi…）
只提供对话接口，没有向量或视觉。如果用一个总开关整体切过去，记忆检索会当场坏掉
（没有向量模型就只剩词法通道）。所以默认只有对话走外部，另外两个要用户显式打开。

**为什么只做 OpenAI 兼容一族。** DeepSeek / 月之暗面 / 智谱 / 通义千问 / 硅基流动 /
OpenRouter / Gemini / Groq / Mistral / xAI / Together / Perplexity / 火山方舟 / 混元 /
星火 / 本机 Ollama / LM Studio 全都提供 `/chat/completions` 这个形状的接口，
差别只在域名与模型名。真正的例外是 Anthropic 的 Messages 协议（报文结构完全不同，
无法复用），按约定不做，需要时用 OpenRouter 中转。

**入向为什么要复用对话管线。** `/v1/chat/completions` 和页面上的 `/api/chat`
共用 `runChatPipeline()`（视觉 → 记忆召回 → 人设 → 流式生成 → 落记忆），
两者只是"事件怎么编码"不同（一个转 SSE 给浏览器，一个打包成 OpenAI chunk）。
写两份迟早会改歪一边 —— 比如只在其中一处加了记忆召回。

**顺带修掉的两个既有问题：**

| 问题 | 表现 | 修法 |
| --- | --- | --- |
| `stripThinking` 只认 `</think>`，而 qwen3 在 Ollama 上吐的是全角竖线的 `<｜end▁of▁thinking｜>` | 流式干净、非流式把思维链糊在正文前面（两条路径的判定对不上） | 两种结束标记都认，并处理"被 `num_predict` 截断、只有开标记"的情形 |
| `lib/memory.js` 记录了 `rec.embedModel` 却从不按它过滤 | 换过向量模型之后，旧向量与新向量不在同一空间，余弦相似度是纯噪声，会以看似正常的分数把不相关记忆排到最前 | 只比较同一 `embedModel` 的向量；`stats()` 另报 `usableEmbedding` / `staleEmbedding`，失效向量仍可由词法通道召回 |

### 2.7 联网协议（V4.1 新增，默认关闭）

让本地模型真的能上网查资料：给它一组工具（function calling），它自己决定查什么、
查几次，我们负责执行并把结果压成它能读的文本喂回去。

```
用户提问
   │
   ▼
lib/agent.js  ── 多轮循环（最多 N 轮，同工具同参数去重）
   │  inference.chatStream({ messages, tools })      ← 本地 Ollama 或外部 API 都支持
   │      ├─ 返回 tool_calls → lib/tools.js 执行
   │      │        ├─ web_search    搜索（Bing → 百度 → DuckDuckGo，无需 Key）
   │      │        ├─ web_fetch     抓网页 → 转纯文本
   │      │        └─ find_panorama 找 360° 全景图（供景区建模用）
   │      │     结果作为 tool 消息回填 → 再问一轮
   │      └─ 不再调用工具 → 这一轮的正文才是**答案**
   ▼
SSE 推给界面：agent_round / tool_start / tool_result / round_discard / delta / done
```

**为什么"过程文字"要单独处理。** 模型调工具前常先吐一句「我先查一下」。
它和最终结论混在一条流里，用户看到的答案开头就是一句没头没尾的自言自语。
所以带工具调用的那一轮，正文会被 `round_discard` 事件从答案区撤走、归入步骤说明。

**为什么必须做 SSRF 防护。** 要抓的网址是**模型生成的**，属于不可信输入。
没有这层，模型（或一次提示注入）只要写一个 `http://127.0.0.1:7860/...`，
就能把本机服务当成它的内网代理去读；写 `169.254.169.254` 则是在探云元数据。
所以：只允许 http/https、只放行 80/443、DNS 解析后拒绝一切内网/回环/链路本地地址、
**重定向逐跳复检**（用 fetch 的自动重定向会跳过校验，等于开后门）。

**为什么工具失败不抛异常。** 模型看不到异常，只会看到空白，然后开始编。
所以失败被包成一条「工具输出」回传（`lib/tools.js` 的 `runTool` 永不抛出），
模型才有机会换个关键词重试。

**两家的工具消息格式不一样，由 `lib/inference.js` 统一。**
Ollama 的 `arguments` 是**对象**、tool 消息不需要 id；OpenAI 兼容接口的 `arguments` 是
**JSON 字符串**、`tool_calls` 要带 `id` 与 `type:'function'`、tool 消息必须回填
`tool_call_id`。写错任何一条，表现都是"模型开始反复调同一个工具"或直接 400，
而报错信息完全指不到格式上去 —— 所以这段逻辑只写一处，并用测试钉住两种形状。

### 2.8 位置与位置 MCP（V4.1 新增）

```
浏览器定位 / 手填 / IP 估算
        │  POST /api/location*
        ▼
  data/location.json  ←── 单一事实来源，带 source 与时间戳
        │
        ├─► 网页：/api/location/relation?spot=灵隐寺
        │         └► 舞台 HUD（罗盘 + 距离）＋ 3D 角色脚下的指北环与方位箭头
        │
        └─► mcp/location-server.js（独立进程，直接读同一个文件）
                  └► get_location / distance_to_spot  →  外部 Agent
```

**为什么两个进程靠"文件"而不是"调用"耦合。** MCP 服务是独立进程，如果让它反过来
HTTP 调本服务，就引入了一个"网页没开着就查不到位置"的隐性依赖。共用一个 JSON 文件
最简单，也最不容易坏。

**位置的"来源"和"时间"必须一起存。** 只存 `{lat,lng}` 会出事：
IP 定位的坐标只到城市级（可能偏几十公里），过期半小时的坐标也不代表"你现在在哪"。
所以记录里带 `source` / `at`，读的时候算出 `ageMs` 与 `fresh`，
界面与 MCP 返回值都会如实说明局限 —— 这类"看起来精确、实则很粗"的数据最容易被误用。

**自己实现 MCP 时最容易踩的坑：stdout 只能有协议报文。**
一个 `console.log` 就会混进 JSON-RPC 流，客户端通常只报"连接异常"，
完全看不出是自己多打了一行日志。所以本项目的 MCP 服务日志一律走 stderr，
并且 `test/mcp-location.js` 里有一条**stdout 纯净性**断言把它钉住。
另外三条：通知不能回响应、工具失败要用 `isError` 而不是 JSON-RPC error、
响应一行一条不做 JSON 美化。

### 2.9 景区全景与深度浮雕（V4.1 新增）

```
用户输入景点
   │
   ├─ 联网：图片搜索（Bing/百度）→ 直链 → 下载 → 量宽高比 → 只留 2:1 左右
   ├─ 上传：用户自己的全景图
   └─ 程序化：离线合成（界面标注"非实拍"）
        │
        ▼
   data/panoramas/<id>.<ext>      全景图缓存
        │
        ├─► /api/pano/image/:id    给 three.js 当环境球贴图
        │
        └─► tools/depth-worker.py  单目深度（Depth-Anything-V2-Small）
                  └─► data/depth/<id>.depth.png   灰度高度图
                            └─► 前端逐顶点推球面半径 → 起伏浮雕
```

**为什么是"推球面半径"而不是"切地形高度图"。**
全景里绝大多数内容是**竖直方向**的信息（天空、远山、建筑）。把它们压成一张地面
高度图，既不符合全景的几何，也必然难看。逐顶点按深度推半径才是与全景几何一致的
做法：近处凸向观察者、远处退到背景，照片里的山与树就成了真有厚度的浮雕。
实测 1024×512 全景、18721 个顶点，半径从 14.1 撑到 41.6。

**为什么判定条件只有"宽高比 2:1"这一条。**
等距柱状投影的定义就是 2:1。比例不对的图贴到球面上会明显变形，而用户只会觉得
"程序坏了"。所以下载之后必须**把图片头读出来量尺寸**（手写解析 PNG/JPEG/GIF/WebP），
不合格的直接丢弃、**不写缓存** —— 否则缓存里会堆一堆废图，下次还优先命中。
只看 URL 后缀是不够的。

**为什么深度跑在 Python 子进程里。**
Node 侧没有可用的深度推理方案，而项目要求 Node 侧零第三方依赖。用子进程把界限
划清楚：Node 只管调度与缓存，Python 只负责"图进、高度图出"。每次调用要重新载模型
（约 0.7 秒），但深度图**按全景图缓存**，同一张景区图只算一次 —— 为 0.7 秒引入
保活、崩溃重启、显存常占这些复杂度不划算。

**一个必须如实说明的现实约束。**
实测中文景点在公开网络上基本找不到可自由获取的等距柱状全景图：中文全景平台
（720云等）只给 JS 查看器不给直链，图片搜索回来的全是普通照片（实测 1.33~2.27
的各种比例）。所以「联网检索」会正确地把它们**全部拒掉并列出逐条原因**，
而不是硬塞一张会变形的图。要真实景演示，走「上传」。

### 2.10 图片转 3D（V4.1 新增）

```
一张图片 → 上传到 data/img23d/<id>.png
    │
    ▼
tools/triposr-worker.py（Python 子进程）
    ├─ 去背景（rembg）—— 失败则改用原图并如实上报，不让整个任务失败
    ├─ TripoSR 推理 → 密度场
    ├─ 等值面提取（**PyMCubes + torchmcubes 垫片**，见下）
    ├─ 轴序置换（TripoSR 的 Z-up → three.js 的 Y-up）
    └─ 导出 GLB
    │
    ▼
models3d.save() 登记进项目已有的模型库
    └─► 直接出现在「外观 → 更换形象」，不需要为生成的模型另造一套管理
```

**为什么不改 vendored 源码。** TripoSR 用 `torchmcubes` 做等值面提取，而它**没有
Windows 预编译包**，自己编译要 MSVC。所以改用 `PyMCubes`，并在 `import tsr` 之前
往 `sys.modules` 注入一个同名垫片。补丁只在一处、显式可见，升级 TripoSR 时只需重看这里。

**两个必须显式处理的坐标/接口差异**（都属于"错了也不报错、只是结果悄悄不对"那一类）：

| 问题 | 表现 | 处理 |
| --- | --- | --- |
| PyMCubes 与 torchmcubes 的顶点轴序相反，而 `isosurface.py` 里已经有一句为后者写的 `[2,1,0]` 补偿 | 等于换了两次轴 → 模型被转置，看上去"朝向有点怪" | 垫片里**预交换**一次。用已知位置的体素验证：不预交换得到 `x=0.801 z=0.199`，预交换得到 `x=0.199 z=0.801` |
| TripoSR 是 Z 轴朝上（`tsr/utils.py` 注释：x back, y right, z up），而 three.js/VRM 是 Y 轴朝上 | 模型导进舞台**侧躺** | 施加**循环置换** `(x,y,z)→(y,z,x)`。它是行列式 +1 的真旋转，不会镜像。用输入图宽高比验证：置换后 X/Y=1.322，输入图 410/310=1.323 |

**显存是这台机器上最现实的约束。** 8GB 卡上、其它程序占着显存时实测：
192/4096 → `CUDA error: unknown error`；160/2048 → 成功（约 1.4 万顶点、1~2 分钟）。
所以默认取 160/2048。另外 CUDA OOM 提示里常建议的
`PYTORCH_CUDA_ALLOC_CONF=expandable_segments:True` **在本机不要开** ——
torch 2.11+cu128 + RTX 5060 上会改成抛 `shared object initialization failed`，更难查。

**贴图那条路有三个坑，都修在被改动的 vendored 源码之外：**

| 问题 | 表现 | 处理 |
| --- | --- | --- |
| `tsr/bake_texture.py` 把位置张量建在 CPU，而 `scene_code` 在 CUDA | GPU 上烘焙必报 `Expected all tensors to be on the same device` —— **官方代码在 GPU 上本来就是坏的** | 在 worker 里把 `positions_to_colors` 换成逐行相同、多一个 device 参数的版本 |
| `xatlas.export` 只写 OBJ 文本，不认 `.glb` | 扩展名是 .glb，内容却是 `v x y z` 文本；模型库校验 glTF 魔数 → **烘焙成功却登记不进去** | 改用 trimesh 建 `TextureVisuals` 网格再导出，贴图内嵌进 GLB |
| 按"要烘焙"取出的网格是 `has_vertex_color=False` | 烘焙失败后直接导出它 → 得到**灰模**（而不是"退到顶点色"） | 失败时重新 `extract_mesh(..., True, ...)` 取带色的网格再导出 |

默认开烘焙（目标是"带贴图网格"），失败才退到顶点色并如实上报。

### 2.11 Blender 动画（V4.1 新增）

```
网页点「生成移动动画」
   │  POST /api/blender/anim
   ▼
lib/blender.js  ── TCP 127.0.0.1:9876，JSON-RPC 风格：{type, params} → {status, result}
   │  命令：execute_code
   ▼
Blender 主线程执行 tools/blender-anim.py
   ├─ 先删掉自己上次生成的（名字带 wenlv_ 前缀）→ 幂等，重复跑不堆积
   ├─ 用基本体搭一个 1.6m 的小人（躯干/头/双臂/双腿）挂在一个 Empty 根上
   ├─ 打关键帧：绕圈巡逻 + 朝向沿切线 + 四肢摆动 + 上下起伏
   └─ 导出 GLB（use_selection=True，只导出自己的对象，不碰用户场景）
   │
   ▼
models3d.save() 登记进模型库
   └─► 网页 three.js AnimationMixer 逐段循环播放（实测 7 段动画、7 个节点被驱动）
```

**为什么必须开图形界面。** 插件源码里明确写了 `blender -b` 下命令永远不会执行 ——
它的命令队列靠 Blender 主线程的定时器排空，后台模式没有事件循环。
所以 `npm run blender:start` 会真的弹出 Blender 窗口，这是前提而非偷懒。

**两个协议层面的坑（都属于"错了不报错、只是拿不到数据"那一类）：**

| 问题 | 表现 | 处理 |
| --- | --- | --- |
| `execute_code` 只回捕获的 stdout，**丢掉 Python 返回值**（实现是 `with redirect_stdout(buf): exec(code)`） | 拿到的是一坨导出日志，不是结构化结果 | 代码里自己 `print` 一行带标记的 JSON，再从 stdout 里解析 |
| 导出日志也混在同一个 stdout 里 | 若取"最后一行"，标记后面还有日志时会解析失败 | **从后往前找标记行**，并且测试里专门钉了"标记后面还有日志"这种情形 |

再加上：**一次命令一条连接**。插件响应是从定时器回调里 `sendall` 出去的，
共用连接时可能交错；每次开新连接换来"响应一定属于这次请求"。

**关于可循环。** 移动动画最易翻车的是首尾不接。所以让小人绕圈巡逻、朝向沿切线，
且关键帧**包含 t=0 与 t=1 两端**。浏览器实测起点与终点都是 `(2.400, 0, 0)`，完全对齐。
（第一版写成 `range(1, frames+1, step)`，最后一帧只到 t=0.972，循环是断的。）

### 2.12 形象动作扩容与导航模式（V4.1 新增）

这一节记录"让 2D 形象做出更多动作、能更好地与用户互动"这件事的**实际形状**，
因为它一开始被误解成一个训练问题。

#### 2.12.1 先纠正一个前提：这不是"训练模型"能解决的

最初的需求是「训练我们的本地模型，让他可以让 2D 形象做出更多的动作」。
但 Live2D 的动作能力由三样东西决定，**没有一样是"训练"出来的**：

| 环节 | 是什么 | 能不能"训练" |
| --- | --- | --- |
| 动作数据 | `.motion3.json` 关键帧文件 | 不能。是美术做出来的 |
| 播放器 | `pixi-live2d-display` | 不能，已有库 |
| 调度 | 什么时候播哪一个 | **这里是真正能改的** |

所以大语言模型在这件事里的角色是**决定播什么**（通过工具调用），不是学会做动作。
真正让"动作变多"的是下面这条数据链，而其中的坑极深。

#### 2.12.2 动作变多的真正做法，与那个最隐蔽的坑

从本机 VTube Studio 导入官方示例模型（`npm run import:vts`），动作从 24 个涨到 57 个。
但**只复制文件是没用的**，这里踩了一个非常隐蔽的坑：

> VTube Studio 的模型用**自家的热键系统**绑动作，`model3.json` 里
> **根本没有 `Motions` 段** —— 只有 `Moc` / `Textures` / `DisplayInfo`。
> 把 `.motion3.json` 文件复制过来，运行时**一个都播不了**。

危险之处在于：磁盘上文件都在，界面上也能列出模型，一切看起来正常，
只是点"换个动作"没有任何反应。**按文件个数统计会得出"有 33 个新动作"的错误结论。**
所以导入脚本会给项目副本补写 `FileReferences.Motions` 声明（名字带 `idle` 的进
`Idle` 组，其余进 `TapBody`），而验证必须**走运行时路径**去数声明，不是数文件。

补写声明时又踩了第二个坑，**同一类问题的两个实例**：

1. 路径用 `path.relative(process.cwd(), f)` 算 → `f` 指向 VTS 安装目录，
   于是 `model3.json` 里写成 `D:/SteamLibrary/.../animations/x.motion3.json`，
   **指回了 VTS 安装**。本机因为 VTS 还在，看起来完全正常；换台机器、或用户卸载了
   VTS，动作全部加载失败，而复制过来的文件压根没被用上。
   改成相对目标目录算也不行 —— 源在 D:、项目在 E:，**Windows 上跨盘符时
   `path.relative` 直接返回绝对路径**。正确做法是相对**源模型目录**算
   （复制时保留了目录结构，相对路径不变）。

2. 口型/眨眼组"已经存在"就不再加 → VTS 的模型里 `LipSync` 与 `EyeBlink` 这两个组
   **是存在的，但 `Ids` 是空数组**（VTS 靠热键绑，不往模型文件里写）。
   只判断"有没有这个组"会以为已经配好了而跳过，结果是**口型不动、眼睛不眨，
   且不报任何错**。所以判据必须是"组存在**且** `Ids` 非空"，缺了就补全。

#### 2.12.3 参数名不能写死

补口型参数时还发现：**口型参数名在不同模型之间根本不一样**。

| 模型 | 口型参数 |
| --- | --- |
| haru / hiyori | `ParamMouthOpenY` |
| Mao | `ParamA`（Cubism 标准的元音口型参数） |
| vts-akari | `ParamMouthOpen` |
| vts-hijiki / tororo / wanko | `PARAM_MOUTH_OPEN_Y` |

原来的 `live2d.js` 把 `ParamMouthOpenY` 写死在每帧循环里。指到不存在的参数上
**不报错、不警告**，只是嘴永远不动。所以现在加载模型时会读同目录的 `cdi3.json`
拿到该模型真实的参数表，再决定驱动哪个。测试里钉了一条
"各模型的口型参数各不相同（≥2 种）"，一旦有人改回写死的常量就会变红。

#### 2.12.4 服务端出意图、前端出画面

`avatar_action`（换表情 / 做动作 / 举牌）这个工具和其它联网工具有本质区别：
**它不产生任何给模型读的信息**，只是把意图打包成 `data` 交给前端执行。

为什么必须这样切分：agent 工具循环跑在**服务端**，而"这只模型有哪些动作、
表情叫什么"只有**浏览器把模型加载完之后**才知道（清单在模型文件里，服务端不解析）。
所以：

- 前端每次提问把能力清单随请求上报（`body.avatar`）；
- 服务端据此把它写进系统提示、并在工具收到不存在的动作名时**把可用清单作为
  错误回给模型**让它自己改 —— 沿用本项目"工具失败也要变成模型能读的说明"的一贯做法；
- 服务端把 `data` 转发给前端（原先 `tool_result` 事件把 `data` 丢掉了，
  那样 `avatar_action` 的效果前端永远收不到）；
- 前端在 `tool_result` 事件里读 `ev.data.avatar` 执行。

一个容易忽略的接线问题：`avatar_action` **不能挂在联网开关下**。它跟联网毫无关系，
挂在 `web.enabled` 下会导致"用户一关联网，连笑一个都做不了"。

#### 2.12.5 程序化待机：两个必须遵守的引擎细节

模型自带的 `Idle` 是定时循环的一段动画，两次之间参数完全静止，看上去像卡住。
所以在参数层面持续驱动（呼吸 / 微摆 / 自主视线 / 定时抽小动作）。两个约束都是
**读打包后的引擎代码**确认的，写错不会有任何报错：

1. 只能在 `beforeModelUpdate` 钩子里写参数。写在 `afterMotionUpdate` 会被紧接着的
   `saveParameters()` 存成新基准值 → **每帧叠加、一路顶到参数上限**
   （表现为越待机越歪、最后定住）。
2. 必须用 `addParameterValueById`（叠加）而不是 `set`。引擎自己的 `updateFocus()`
   正是用叠加把"看向鼠标"写进 `ParamAngleX` 等参数的，`set` 会把鼠标跟随整个抹掉。

代价：`physics.evaluate()` 在钩子之前跑，衣服/头发不会跟着微摆甩。为满足第 1 条
而接受的取舍。

#### 2.12.6 导航模式：素材的合法性边界

导航模式要"形象举牌显示目标景点 + 背景跟着换"。这里有一条**刻意划出的边界**：

VTube Studio 的 `Items` 目录里有现成的木牌 PNG（约 120 张），直接拿来用最省事 ——
但那些是**第三方作者的作品**（文件名里带着 `@MoshieStudio`、`@catboymee` 等署名），
拷进项目里分发不合适。所以牌子改成**用代码画**：Canvas 2D 画木板纹理 + 四角圆钉 +
自动折行（放不下就缩字号）的中文牌面 + 一根木杆。

风景图三种来源，其中联网那档**默认关闭且必须手动点「应用」**，受全局联网总开关
节制；搜到的图先下载到 `data/scenery/cache/` 再交给前端 —— 直接热链外站图片的话，
链接随时可能失效，用户断网后整个背景也废了。任一路径失败都**退回内置程序化风景**
并说明原因，而不是留一片空白。

绘制代码放在 `public/js/nav-visuals.js` 而不是各自的渲染器里：Live2D 用 PixiJS、
3D 用 three.js，对象模型完全不同，但"牌子长什么样""风景怎么画"是**纯 2D 绘制**，
跟渲染器无关。两边各写一份，改个木头颜色就要改两处。

### 2.13 听觉：本地 Whisper 语音输入（V4.1 新增）

与 2.12 是一对：那一节让它**动**，这一节让它**听**。

#### 2.13.1 为什么格式转换放在前端

浏览器能录的格式（webm/opus）不是服务端容易解的格式。服务端要解它就得依赖
ffmpeg —— 这台机器上不一定有，装一个又是几十分钟。所以链路是这样切的：

```
MediaRecorder 录 webm/opus
   → 前端 AudioContext 解码
   → 重采样成 16kHz 单声道 16-bit WAV
   → base64 → POST /api/stt
   → 服务端只读 WAV（Python 标准库 wave 模块就够）
```

代价是前端多了一段混音/重采样/PCM 打包的代码（`public/js/voice.js`），
换来的是**后端零额外依赖**。这与项目"零第三方 Node 依赖"的整体取向一致。

#### 2.13.2 开关放在库层面，不是路由层面

`lib/stt.js` 的 `transcribe()` 在**做任何工作之前**先查开关，关着就直接返回
`STT_DISABLED`（连临时音频都不落盘）。路由里不重复判断 —— 单一判断点。

这么放是有意的：如果把判断写在路由里，那么将来任何别的调用方（MCP 服务、
命令行工具、对外开放的 `/v1` 兼容层）都会绕过去，"默认关闭"就成了只对网页
界面成立的假承诺。

#### 2.13.3 测试为什么必须分层

听觉的测试分成两层，因为"真起 Python"的代价太大：

| 层 | 内容 | 默认 |
| --- | --- | --- |
| 纯 JS | WAV 头解析、重采样、base64 解析、开关与失败路径的中文报错、临时文件清理、worker 的两种失败契约 | **跑** |
| 真 Python | 真实排队行为、环境探测（`import torch`）、端到端识别（载 ~1GB 权重） | 跳过，`STT_REAL=1` 开 |

不分层的话，光一次 `import torch` 就要十几秒、载模型动辄几分钟，
`npm test` 会慢到没人愿意跑 —— 最终结果是**整个测试套件被绕过**，比少测几条更糟。
（这一点是实测的：分层前 `node test/stt.js` 跑 120 秒都没结束。）

还有一条经验值得记：**"完全没有 Python"这个分支没法靠构造环境来测**。
Python 候选里有一条硬编码的本机路径（`E:\AI\qwen-tts-webui\python`），
只要它还在，探测就一定会成功。第一版测试试图用"改 `WENLV_PYTHON` +
清空 `PATH`"来构造，结果拿到的错误是"缺权重"而不是"缺 Python"，测试红了才发现。
正确的做法是把这段文案的拼装抽成纯函数 `unavailableReason()` 直接喂参数验证 ——
**测逻辑，而不是测环境**。

顺带发现一个真实的优先级问题：Python 与权重都缺时，原来只报"缺权重"，
用户会去下 1GB 权重然后依然跑不起来。所以顺序固定为**先报 Python、再报权重**。

### 2.14 显存仲裁、西湖主题与两套开屏（V4.2 新增）

这一节记录一次面向「西湖文旅大屏宣传」的整体改造。它的核心不是加功能，
而是解决一个**在 8GB 卡上必然会撞、但报错完全不指向真因**的问题。

#### 2.14.1 显存：五个子系统抢一张卡

本机 8GB 显存，而项目里有五处要用同一张卡：Ollama（对话/视觉/向量）、
Qwen TTS、Whisper、TripoSR、深度高度图。

爆显存的表现极其难查 —— 报错会指向**别处**："模型没完全装进显存"、
"被别的程序抢了算力"、CUDA out of memory 栈，甚至只是慢得离谱。
用户看到"随机失败"，开发看到"本地明明跑通过"。

`lib/gpu.js` 用一把**进程内的读写锁**解决：

| 角色 | 谁 | 语义 |
| --- | --- | --- |
| 独占（writer） | TTS / Whisper / TripoSR / 深度图 | 同一时刻只允许一个 |
| 共享（reader） | Ollama 的对话/视觉/向量 | 独占期间必须等 |

三个设计决定值得单独说：

1. **写者优先。** 一旦有独占在排队，新来的共享请求要让路。
   否则界面上持续提问会让"图片转 3D"永远排不上队（读者饿死写者）。
2. **Ollama 让位 + 预热防抖。** 光排队不够 —— 显存里可能还躺着 5GB 的对话模型。
   所以拿到独占租约后先 `keep_alive: 0` 请它出去，干完再热回来。
   两个细节：卸载**不是立刻生效**（要等一个 settleMs 再启动 Python，否则撞残留占用）；
   预热要防抖（连跑三个独占任务不能"卸-装"三次）。
3. **关掉仲裁必须零开销。** 显存充裕的机器关掉它只是图省事，
   如果还照做让位与等待，那是帮倒忙。

实现过程中测试抓到过一个**死锁**：`drain()` 里判断能否放行共享请求时，
多要求了"等待队列为空"，于是队列里的共享请求永远等不到人唤醒它 —— 实测卡满 120 秒。
判据只能是"有没有独占挡着"，不能把"有人在等"也当成不能放行的理由。

#### 2.14.2 本地优先：两条路的资源不在一池

外部 API 的接入方式做了三点明确：

1. **默认全走本地**，外部只按用户在「设置 → 模型接入」里逐项指定时启用。
2. **外部调用不经过本地显存闸门。** 这条容易写反：把外部也拉进队列，
   等于让"配了外部 API 来分流"这件事反而更堵。两条路的资源根本不在一个池子里。
3. **三项能力全切外部时释放本地显存。** 本机模型完全用不上却还按
   `keep_alive`（30 分钟）占着约 5GB。判据刻意是"三项全外部"而不是"对话是外部"——
   绝大多数外部供应商只有对话接口，视觉与向量仍走本地，只看对话就卸载会把
   记忆检索当场打回冷启动，属于"越优化越慢"。

`/api/status.ollama.localFirst` 直接给出结论，不让前端复刻判断逻辑：
复刻错了会显示"走本地"而实际走了外部，那等于让用户在一个错误前提上做隐私判断。

#### 2.14.3 西湖形象：为什么是"画"出来的

用户要求把虚拟形象换成适合宣传西湖的。直接找现成的西湖主题角色模型有两个
绕不过去的问题：

1. **授权。** 能搜到的国风角色模型绝大多数是画师/建模师的作品，明确禁止商用或
   未标明授权。项目要拿去做对外宣传，用授权不明的角色站台，风险远大于美术成本。
2. **拿不到。** 本机能访问的镜像里没有西湖主题的角色模型；VRoid Hub 需要登录；
   Wikimedia 那条路在这台机器上直接不通（连接失败）。

所以 `public/js/lake.js` 里用代码画了一个原创「西湖船娘」：汉服、发髻簪花、
执油纸伞，配色取自西湖青绿山水。参数化绘制（呼吸/微摆/视线/口型/6 个动作都是
参数插值），矢量所以任意分辨率都不糊。

它是**第三套舞台**，接口与前两套（Live2D / 3D）完全对齐 —— 这正是最容易出错的地方：
少实现一个方法，用户切过去就 `xxx is not a function`。所以 `test/display.js` 里
有一条 17 个方法的交叉校验，逐个数三套舞台是否都实现了。

同时把内置角色卡的默认形象从 `nahida` 改成它 —— 顺带发现那个 `nahida`
在本项目里**根本不存在**，等于默认形象一直是坏的，靠兜底才没露馅。

#### 2.14.4 视频背景：为什么不做联网找片

项目里其它素材（全景图、风景图）都留了联网搜索的口子，视频**没有**：

1. 能免费拿到的西湖实拍视频，多半来源或授权不明。宣传片是对外展示的，
   版权出问题的代价远大于省下的事。
2. 视频动辄几十上百 MB，走"搜索→下载→校验"失败率高、等待久，
   不如让用户直接把自己手上的片子拖进来。

所以做的是：`data/videos/` 自备目录 + 上传，以及**程序化生成的西湖动态画面兜底**
（目录为空时不会黑屏）。播放用真 `<video>` 而非画进 canvas：交给硬解码器、
4K 不吃主线程、`object-fit: cover` 直接解决"铺满不变形"。
服务端接口支持 **Range** —— 不做的话浏览器拖进度条会废，甚至直接拒绝播放。

#### 2.14.5 两套开屏：关于"套用游戏界面"的边界

用户提出"套用游戏《米塔》的开始界面"。这里有一条**必须守住的边界**：
可以直接照搬商业游戏的界面素材、字体、UI 元素是**不能做的**。

所以模板 B 的做法是：采用同一种**排版思路**（暗色环境、角色居侧、竖排菜单、
悬停有反馈），但全部用本项目自己的 HTML/CSS 与程序化绘制的形象实现，
一个第三方素材都不用。`test/display.js` 里钉了一条"boot.js 不含任何外链与第三方
游戏素材引用"来防止以后有人图省事直接贴图。

两套模板的差别不只是皮肤：模板 A 的背景是**不透明**的（整屏视频），
模板 B 的背景**透明**，让底下真实舞台上的形象露出来 —— 这样菜单悬停触发的是
**真形象的真动作**，而不是再渲染一份。少一份渲染，也少一处会不同步的地方。

开屏状态持久化两条：用哪套模板、"是否已进入"。后者很重要 ——
每次都弹的话用户三分钟内就会去关掉它；所以一次会话只自动弹一次。

### 3.2 为什么走"新增页面"而不是写 AIRI 插件

调研结论（见那份交付物里的决策记录）：

- AIRI 的插件体系（`packages/plugin-sdk` 的 Eventa extension host）在浏览器端只支持
  `in-memory` 传输，`packages/plugin-sdk/src/plugin-host/runtimes/web/index.ts`
  对其余传输方式直接 throw。
- `apps/stage-web` 的 `package.json` 根本没有引入 `@proj-airi/plugin-sdk`，
  构建产物里也不含插件宿主。

也就是说：web 端当前无法加载插件。而文件路由只新增文件加两行插入，
改动最小，改完 build 一次即可生效。

### 3.3 机体记忆在 AIRI 里的现状与本项目的补法

AIRI 的「机体记忆」目前是空的：

- `packages/memory-pgvector`：24 行的占位实现，没有任何地方 import 它，
  没有 schema、没有 `CREATE EXTENSION`、没有向量查询代码。
- 设置页的 `settings/modules/memory-long-term.vue` 和 `memory-short-term.vue`
  只有 16 行的 `<WIP />`。
- 真正在用的"记忆"是 IndexedDB 里的聊天历史（`chat/session-store.ts`）。

本项目的补法是把长期记忆放进本仓库已经写好的本地记忆服务（`lib/memory.js`），
再通过 `airi-bridge` 的 `/memory/*` 暴露出去，AIRI 侧和任何 Agent 都能读写。

### 3.4 检索算法：混合检索

```
存储：data/memory.json（原子写：先写 .tmp 再 rename，防写一半断电丢全部记忆）
落库：写记忆立即返回，向量在后台补算（不阻塞对话）

检索（query → 结果）：
  通道一 · 词法（永远可用）
    中文按「字符二元组」滑窗切分，英文/数字按词切分
    score = Σ (1 + log(tf)) × idf × qtf
    时间衰减：exp(-ageDays / 14)，半衰期两周，让"最近聊过的"更容易被想起
    标签命中额外 +1.5（用户显式打的城市/业态标签比正文更可信）

  通道二 · 语义（装了向量模型时）
    Ollama /api/embeddings 取向量 → 余弦相似度

  融合：两条都可用时 0.4 × 词法归一化 + 0.6 × 语义；只有词法时就是词法分
```

中文得单独写一套词法检索，原因是中文没有空格分词：按英文那套空格切词会把整句
当成一个词，检索几乎必然失效。字符二元组是零依赖条件下最稳的中文近似分词方案。

## 四、关键取舍一览

这些是设计过程中真正纠结过的点。每一条都把代价一起写出来。

| 取舍 | 备选方案 | 为什么这么选 | 代价 |
| --- | --- | --- | --- |
| 记忆用本地文件而非 pgvector | Postgres + pgvector | 赛题要求"一键部署"。为向量检索逼用户再装一套数据库，代价远大于收益；混合检索在缺向量模型时也能用 | 实体规模上万条后检索会变慢，目前 117 条是毫秒级 |
| 关掉思考链（`think: false`） | 保留 `qwen3` 的思维链 | 本机是 CPU/GPU 混合推理，开思考出一份 2 天行程 > 5 分钟；且思维链会挤占 `num_predict`，正是原项目记录的"长方案写不满"的诱因之一 | 需要时可 `OLLAMA_THINK=1` 打开；复杂推理题上不如带思维链稳 |
| 输出质检"标注"而非"删除" | 静默剔除未核实项 | 静默删除会让人以为输出 100% 可信，比标注更危险；标注还能变成"样本库待补充清单" | 界面会出现告警条，不如"干净"的输出好看 |
| 前端零框架（原生 DOM） | Vue / React | 与"一键部署、零第三方依赖"的目标一致；不需要构建步骤，改完刷新即可，评委也看得懂 | 组件复用靠手写，状态管理全靠约定 |
| 词云数据放服务端 | 前端写死 | 词云与右侧表单共用 `OPTIONS` 常量，不可能对不上 | 改词要重启服务 |
| 词云默认只留骨架 | 68 个词一次全摆出来 | 一次全展示会糊成一团。默认露 17 个（12 个分组标签 + 5 个核心词），其余悬停预览、点开展开 | 新用户第一眼会觉得"词怎么这么少"，需要一句引导 |
| 条件词"选中但不立刻生成" | 点了就出结果 | 点了就跑的写法凑不出「杭州 + 舒适 + 亲子」这种组合 | 多一步：凑完条件还得再点核心词 |
| 多选只开给「兴趣」组 | 所有条件词都可多选 | 兴趣天然叠加；城市、预算、人群本来互斥。这一条和右侧表单的 `data-multi` 保持一致 | 忌口想同时选"素食 + 忌辣"做不到，只能取其一 |
| 结果卡放底部四分之一 | 右侧窄面板 / 居中弹窗 | 不挡人物；居中弹窗会盖住舞台；右侧面板只有巴掌宽，八列的行程总览表会被压成竖条 | 底部空间有限，长方案要滚 |
| 结果卡按结构分三种走法 | 见到多个 h2 就分两列 | 行程方案有 7 个 h2，「行程总览」是 8 列表格，分半列后每列只剩约 75px，字全被压成竖条 | 排版逻辑要认识内容结构，换一种输出结构就得跟着改 |
| 词云布局自己写（螺线 + 矩形碰撞） | d3-cloud / wordcloud2.js | 零依赖是明确目标；而且需要"按分组渐进披露""词本身带上下箭头控件"这些现成库没有的行为 | 极端长词、极窄屏、词条上百时不如成熟库稳 |
| `num_ctx` 统一成 16384 | 每个调用点各自设 | Ollama 按 `(模型, num_ctx)` 分别缓存 runner，值不一致会导致每次切换都重新加载权重（实测 2.3~2.6 s） | 显存占用比按需设置高；视觉模型也跟着吃了大 ctx |
| 服务只监听 `127.0.0.1` | 监听 `0.0.0.0` | 数据不出本机，局域网也访问不到 | 想在手机或平板上演示得改 `HOST` |
| 样本库用 Markdown | 数据库 / JSON | 换成本地真实业态只需改表格，不用碰代码；非技术岗也能维护 | 没有字段校验，列写错也不会报错 |
| 模型不随仓库分发 | 把示例模型打进仓库 | 版权在第三方（Live2D Inc. / VRM Consortium），项目不该替使用者做分发 | 第一次跑要先下载约 33 MB 模型 |
| Live2D 预览图离线生成 | 运行时实时渲染 | 单张纹理 2~3 MB，让前端给每个模型都起一个渲染器太贵 | 换模型后要手动跑一次生成脚本 |
| 生成流按 80ms 节流 | 每条 delta 都渲染 | 一次方案有 500 多条 delta，每条都把整篇 markdown 重渲一遍是 O(n²) | 文字成块跳出来，不是一字一字蹦 |
| AIRI 侧只加页面不加插件 | 写 AIRI 插件 | web 端加载不了插件（见 3.2） | 只能改源码，升级 AIRI 时要重新打补丁 |
| `pnpm install --ignore-scripts` | 完整 install | `sharp@0.29.3` 需要 MSVC C++ 工作负载，无 VS 的 Windows 上必然失败；stage-web 构建用不到它 | 若某个包真的依赖 postinstall，得单独处理 |

下面这组是早先版本测的，留作对照。它比现在慢一个量级，原因是 qwen3:8b

| 场景 | 耗时 | 备注 |
