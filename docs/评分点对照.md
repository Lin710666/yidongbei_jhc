## 一、场景适配性（30 分）

### 对应赛题要求

赛题「4.题目介绍」原句（5 项规定能力和 1 条专业适配要求都写在这一段里）：

> 系统需通过轻量化智能 Skill 协同工作，实现文旅场景智能咨询应答、个性化游玩旅居餐饮方案智能规划、
> 文旅营销内容智能生成、特色文创与服务产品创新赋能、客源需求精准匹配，覆盖景区服务、酒店旅居、
> 餐饮消费、文旅营销、产品研发等全业务场景，适配旅游管理、文化创意、数字媒体等相关专业实训应用。

赛题「5.答题要求(1)」原文：

> 针对文旅行业景区、酒店、餐饮核心业态中消费体验同质化、客源转化效率低、产品创新迭代慢三大痛点，
> 开发 1-2 项核心文旅智能化场景功能，聚焦游客消费体验升级、文旅营销创收增效、文旅文创创新迭代三大核心场景。

### 三个痛点分别怎么解

赛题这段点了三个痛点。逐条回应如下，不用评委自己去连线。

| 赛题痛点 | 本项目的解 | 为什么这样能解 | 怎么验证 |
| --- | --- | --- | --- |
| 消费体验**同质化** | 方案不是模板套壳：按预算 / 同行人群 / 兴趣 / 饮食禁忌到本地样本库里筛条目，条件变了，行程跟着变 | 同质化的根子是"所有人拿到同一份推荐"。这里的推荐项来自本地业态库，筛选条件由用户自己在词云上点出来 | 同样选「杭州 2 天」：一组「亲子 + 忌辣 + 自然风光」、一组「情侣 + 文艺打卡」，实测两份行程的午餐、下午、晚餐都不同，只共享了西溪湿地上午这一项 |
| 客源**转化效率低** | 营销素材一次生成五个平台的通用文案，并给 A/B 两个版本 | 转化看的是"投得动、测得了"。直接给可用稿加双版本，省掉人工改写、也省掉从头写第二版 | 同一个文创主体，抖音版和公众号版写法不同；结果卡里 A/B 两列并排，一屏可对比 |
| **产品创新迭代慢** | 营销主体含「文创创意」「活动策划」两类，样本库 `marketing-playbook.md` 给创意方向与卖点提炼套路 | 产品迭代慢往往卡在"想不出做什么"。这里先把创意方向和卖点角度摊开，作为产品研发的输入 | 选「文创创意」主体生成文案，可看到独立于景区/酒店的创意方向与卖点角度 |

> 前两条是直接解决。第三条是间接支撑：本项目产出的是**创意方向与卖点角度**，
> 不是可以直接投产的文创产品设计。这一点不夸大。

### 本项目的实现

（1）核心功能取赛题写明的 1-2 项上限，做满 2 项并各做深：两项都接了本地样本库约束和输出质检，
而不是铺开做五个半成品。其余入口（对话、记忆、视觉、语音）是围绕这两项功能的支撑能力，
不另算核心功能。

| 核心功能 / 场景落点 | 对应赛题场景 | 实现位置 |
| --- | --- | --- |
| 个性化方案规划 | 游客消费体验升级 | 「文旅功能」页签 → 方案规划 |
| 文旅营销素材生成 | 文旅营销创收增效 | 「文旅功能」页签 → 营销素材 |
| 文旅文创创新迭代 | 由营销的「文创创意」「活动策划」两类主体承载 | 词云「营销产品」组 |

（2）样本库按业态组织：`.agents/skills/wenlv-assistant/references/` 下按
景区（`destinations.md`）/ 酒店民宿（`hotels.md`）/ 餐饮（`dining.md`）三类分库，
覆盖 5 座城市共 117 条实体。字段包含门票、时长、最佳季节、适配人群、
价位档、禁忌友好度等真实业务字段。

（3）交互形态贴合"服务"语义，而不是"填表"语义：原项目是一个表单页；
本项目改成虚拟向导站在页面上。用户像跟导游说话一样提需求，
点词云上的「杭州」「亲子」「忌辣」就能拼出需求，向导会用语音念出方案。
这直接对应赛题"解决传统文旅行业人工服务刻板、客群需求适配度低"的表述。

（4）五业态覆盖：营销功能支持 景区 / 酒店 / 餐饮 / 文创 / 活动 五类主体，
对应赛题的"文旅文创创新迭代"。

（5）形象与场景可换，适配不同讲解场合：内置 3 套 Live2D 人物形象
（含 Project AIRI 自带的基础建模 桃瀬ひより 免费版 / Pro 版）与 12 个背景
（3 张 AIRI 图片 + 9 个程序化场景：极光 / 波浪 / 樱花 / 星野 / 点纹 /
山水青绿 / 暖金黄昏 / 宣纸留白 / 纯色），并支持上传自己的图。
讲古镇可以配「山水青绿」，做夜间市集推广可以配「暖金黄昏」，
录屏出图可以配「宣纸留白」。同一套系统能贴合不同文旅场景的调性，
而不是无论讲什么都长一个样。
角色卡里也能绑定形象，做"一角色一造型"。

## 二、功能实用性（25 分）

### 对应赛题要求

> 有效解决行业高频痛点，提升服务效率。

这句含两个诉求：**解决高频痛点** → 见（1）（5）（6）；**提升服务效率** → 见（7）与下面的指标点。

### 本项目的实现

（1）输出可直接落地：模型被硬性约束只能逐字引用样本库里的
名称（见 `lib/wenlv.js` 的 `OUT_RULES.plan` 第 1 条），
每天字段要求"只写名称本身 + 括号补充"，禁止写成一整句话。
实测输出形如：

```
- 上午：西湖（环湖）（免费，断桥、苏堤、音乐喷泉）
- 午餐：知味观（约40元，小笼包、猫耳朵、定胜糕）
- 住宿：青芝坞·山居民宿（约480元/晚，文艺、近浙大、咖啡馆扎堆）
```

（2）A/B 双版本文案：营销功能一次输出"理性卖点版 + 感性情绪版"，
每版含标题、正文、话题标签、配图建议、CTA，运营人员可以直接拿去 A/B 投放。

（3）一键导出：结果可导出为 Markdown，数据不出本机，可二次编辑。

（4）千人千面：由本地大模型生成，不是规则模板拼接。输入相同的需求两次，
输出不会完全一样。

（5）语音播报：向导可以用本机 Qwen TTS 把方案念出来，这对应"人工服务刻板"的
痛点，让服务有"人味"。默认音色「小文 · 温柔讲解」是为文旅讲解场景专门定的。

（6）看景识景：本机多模态模型可以看懂游客上传的照片，直接给出文旅建议。

（7）服务效率：方案和文案都是边生成边显示的，不是转圈等一大段。实测 2 天方案
首字 0.1~1.2 秒就到，全文 15~25 秒；营销文案首字 1.2 秒、全文 10 秒。
运营人员不用盯着空白页等一整分钟。（`/api/quick-plan` 那个非流式接口要整段返回，
是给 Agent 调用的，不参与页面交互。）

### 指标点

| 指标 | 数值 / 证据 |
| --- | --- |
| 单次方案生成时长（实测） | 2 天方案流式：首字 0.1~1.2 s、全文 15~25 s；营销文案：首字 1.2 s、全文 10 s。非流式的 `/api/quick-plan` 17.5 s（本机 `qwen2.5:7b`，模型已预热，多次实测） |
| 生成内容结构核对项 | 天数是否写满、总览表是否有数据、费用预估三列是否齐、章节是否重复（由输出质检逐项核对） |
| 编造内容拦截 | 7 类输出质检，把未核实项如实标注而不是静默放行 |
| 支持天数 | 1~7 天 |
| 营销平台差异 | 5 个平台各有独立文案特征与结构模板 |
| 语音缓存命中 | 同一句话第二次合成直接读本地缓存（响应头 `X-TTS-Cached: 1`） |

## 三、部署便捷性（15 分）

### 对应赛题要求

> 安装简单、调试快速、环境兼容好。

这句含三个诉求：**安装简单** →（1）（3）；**调试快速** →（5）的排查表与自检点；**环境兼容好** →（4）和指标点里的跨平台一行。

### 本项目的实现

（1）交付物 ② 一键启动、零第三方依赖：本仓库没有任何 npm 依赖
（`package.json` 的 `dependencies` 是空的），只用 Node 内置模块。
双击 `start.bat` 即可，无需 `npm install`，无需构建步骤。

（2）交付物 ① 一键构建（属另一份交付物，不在本仓库内）：`airi/一键构建.bat` 或
`pwsh -File scripts/build-airi.ps1`，自动完成
克隆 → 打补丁 → 装依赖 → 构建工作区包 → 构建前端 → 补 Cubism Core，
每步有明确的成功/失败提示，失败即停。

（3）依赖全部可选：视觉模型、向量模型、语音服务缺哪个都能跑，
界面上用橙色状态灯标出，并给出对应的 `ollama pull` / 启动命令。

（4）构建踩坑已固化进脚本（这是"环境兼容好"的实际内容）：

| 坑 | 脚本里的处理 |
| --- | --- |
| `sharp@0.29.3` 需要 MSVC C++ 工作负载，无 VS 的 Windows 上必然失败 | 改用 `pnpm install --ignore-scripts`（stage-web 构建不需要它） |
| pnpm 每次运行前会重跑 install，又卡回上一行 | 写 `.npmrc` 的 `verify-deps-before-run=false` |
| AIRI 的 Cubism SDK 下载插件只写 `.cache`，`dist` 里 `Core/` 是空目录 | 构建脚本第 5 步显式兜底复制 |
| 部分包导出 `./dist`，不先构建工作区包就构建前端会失败 | 脚本固定顺序 `build:packages` → `stage-web build` |
| `.bat` 里的中文在 cmd 下乱码/解析崩掉 | 所有 `.bat` 存为 GBK/936，开头 `chcp 936 >nul`，用 `ping` 代替 `timeout`，用 `goto` 代替括号块 |

（5）零基础分步教程：`docs/部署教程.md` 每一步都有 ✅ 预期结果 自检点，
末尾有 15 条「常见问题排查表」。

### 指标点

| 指标 | 数值 / 证据 |
| --- | --- |
| 交付物② 部署步骤数 | 3 步（装 Node → 装 Ollama 拉模型 → 双击 start.bat） |
| 交付物② 第三方依赖数 | 0 |
| 交付物② 首次可运行时间 | < 5 分钟（模型已存在时 < 1 分钟） |

## 五、异常处理能力（10 分）

### 对应赛题要求

> 可应对信息缺失、网络异常、操作错误等情况。

这句点了三种情况：**信息缺失** →（1）；**网络异常** →（4）（含 Ollama 未运行 / 生成超时 / 语音服务未启动）；**操作错误** →（5）。

（2）（3）是赛题没点名、项目额外做的两项：目的地不在样本库时降级但不装懂、模型编造内容时拦下并标注。

### 本项目的实现

（1）信息缺失：一次性集中追问（带可点选选项）。
前端有专门入口：词云上的「让 AI 先问我」，不填任何需求直接点，
服务端走 `type=intake` 分支，只把 `SKILL.md`「2.2 需求采集」的规则交给模型，
让它按规范输出一次性集中追问，每个字段都带可点选候选。
这一条在界面上能直接演示：点「让 AI 先问我」，模型会按 2.2 的规则一次把问题问完。

（2）目的地不在样本库：降级但不装懂。
`lib/wenlv.js` 的 `sliceCitySection` 找不到目标城市时，
注入的是明确指令："退回通用文旅知识生成，并在结果开头标注
『本地样本库暂无该目的地，以下为通用建议，建议补充本地数据』"。
演示方法：把目的地改成杭州以外的任意城市。

（3）模型编造内容：输出质检拦下并标注。
7 类自动核对（详见 `docs/架构说明.md`）：

| 质检项 | 判定方式 |
| --- | --- |
| 推荐项是否来自样本库 | 三类分库白名单逐个核对 |
| 条目类别是否用对 | 午餐/晚餐只允许餐饮库，住宿只允许酒店库，上午/下午只允许景区库 |
| 天数是否写满 | 请求 N 天却只有 M 段 `## Day` |
| 总览表是否有数据 | 数据行数为 0 |
| 字段是否被占位符敷衍 | 统计「无 / 待定」与整段缺失比例 |
| 章节是否重复 | `##` 级标题是否重名 |
| 表格列数是否与表头一致 | 逐表比对 |

（4）系统级异常：按类型返回不同状态码，不一律 200

| 异常 | HTTP | 前端表现 |
| --- | --- | --- |
| Ollama 未安装/未运行 | 502 | 状态灯变红，显示安装/启动命令 |
| 模型未下载 | 503 | 状态灯变橙，显示 `ollama pull xxx` |
| 生成超时 | 504 | 提示已等待秒数 + 建议先 `ollama run` 预热 |
| 未启动本地服务 | — | 状态灯变灰，提示"请双击 start.bat" |
| 模型返回为空 | 502 | 提示重试 |
| 畸形 URL（如 `/%`） | 400 | 服务保持存活（原项目旧版会直接崩服） |
| 请求体非法 JSON / 非法 type / 过大 | 400 / 400 / 413 | 明确文案 |
| 图片过大 | 413 | 前端先降采样；后端再校验 |
| 端口被占用 | — | 友好提示 + 换端口建议 |
| 语音服务未启动 | 502 | 明确说明如何以 `--api` 启动 Qwen TTS |
| 视觉模型未安装 | 503 | 明确给出 `ollama pull qwen2.5vl:7b` 等三个候选 |
| 记忆文件损坏 | — | 备份为 `memory.corrupt.json` 后从空记忆继续，服务不崩 |
| 角色卡文件损坏 | — | 备份后恢复内置角色卡，服务不崩 |

（5）操作错误防护：
- 生成期间全局禁用按钮（本机显存有限，重复点击会互相拖慢）；
- 提供「停止」按钮可中断流式生成；
- 输入矛盾（如预算与需求冲突）由 `SKILL.md`「四、异常处理」要求模型指出冲突点并给两套方案；
- 越界/无关请求、危险内容：`SKILL.md` 要求礼貌说明范围 / 拒绝生成并说明理由。

| 指标 | 数值 / 证据 |
| --- | --- |
| 覆盖的异常类型 | 13 类系统级 + 6 类模型级 |
| 错误码到状态码的映射 | 18 个业务错误码 → 400/404/413/502/503/504/500 |

## 八、已知的局限

不想夸大成"什么都能做"。以下都是明知而未在本版解决的问题：

| 局限 | 现状 | 影响 |
| --- | --- | --- |
| 非流式接口要整段返回 | `/api/quick-plan` 端到端实测 17.5 s（2 天方案） | 这个接口是给 Agent 调用用的，要等整篇生成完才返回；页面走的是流式接口，首字 0.1~1.2 s、全文 15~25 s |
| 舞台动画会和 Ollama 抢算力 | Live2D、粒子背景、词云动画都在吃 GPU/CPU。实测在**软件渲染**的浏览器里，同一个生成请求会被拖慢数倍（最长到 300 s 撞超时） | 直连接口 15~25 s；真机开了 GPU 加速时影响小得多。演示前可以把舞台动画关掉（「外观」页签） |
| 长天数方案仍可能写不满 | 7 天方案在 7B 级模型上仍可能提前收尾（实测 5~6 天） | 已由输出质检主动告警"请求 N 天、实际只生成 M 天"；2~3 天方案稳定写满 |
| 输出质检是"检查"而非"纠正" | 只做白名单核对与结构检查，不修改模型输出 | 能发现并标注编造内容，但不能阻止模型生成它；根治需要更强约束或更大模型 |
| 无并发控制 | 多个请求同时打到 Ollama 会互相拖慢 | 前端已用"生成期间禁用按钮"缓解 |
| 单轮生成（方案接口） | 文旅生成接口每次请求独立 | 不支持"把 Day 3 换个餐厅"这类追问式修改；对话页签是带上下文的，可以在那里追问 |
| 样本库为示例数据 | `.agents/skills/wenlv-assistant/references/` 按城市分节，5 城数据为公开常识整理（票价标「约」） | 正式使用需替换为本地真实业态数据；服务端只注入所选城市那一节，扩充城市不挤占上下文 |
| 本机显存吃紧 | qwen3:8b 与 Qwen TTS 1.7B 同时加载时显存紧张 | 建议把 Ollama 与 TTS 错峰使用，或换更小的模型（`qwen2.5:3b` / `0.6B-CustomVoice`） |
| AIRI 侧未接长期记忆的自动写入 | 提供了 `/memory/*` 接口，但 AIRI 的对话链路没有默认调用它 | 需要在 AIRI 侧再接一层（属于 AIRI 本体改造，超出本次范围） |
