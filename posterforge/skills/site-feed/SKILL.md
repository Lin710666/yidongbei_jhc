# Skill: site-feed（联网素材与实时更新）

## 什么时候用

主页需要"看起来在更新"的内容流，或者要给客户看**当前流行的画面风格**做参考。

## 关键立场：不假装能拿到可商用免费素材

实测（2026-09，本机网络）过的源：

| 源 | 需要 key | 实测结果 | 用途 |
|---|---|---|---|
| **Bing 每日壁纸** | 否 | ✅ 每天更新、1920×1080 实拍、带中文标题与版权署名 | 灵感参考 |
| Lorem Picsum | 否 | ✅ 可用，但大量办公/静物，与文旅不搭 | 灵感参考（默认关闭） |
| Pexels | 是 | 需 `PEXELS_API_KEY` | **可商用素材** |
| Unsplash | 是 | 需 `UNSPLASH_ACCESS_KEY` | **可商用素材** |
| Bilibili 搜索 | — | ❌ 无签名返回 412（需 WBI 签名），不适合做稳定源 | — |
| Wikimedia | — | ❌ 本机 SSL 握手失败 | — |

**Bing / Picsum 的图有版权**（Getty、Adobe Stock 等），
所以每张都**强制显示署名**，区块底部统一标注
"仅作灵感参考，不可直接用于商业交付"。这不是客套，是必须守住的边界。

## 接口

| 方法 | 路径 | 说明 |
|---|---|---|
| GET | `/api/feed` | 返回缓存；过期则联网刷新；失败降级返回旧缓存 |
| POST | `/api/feed/refresh` | 强制联网刷新 |
| GET | `/api/img?u=<远程URL>` | **图片代理 + 磁盘缓存** |

## 为什么需要图片代理

不是多此一举，是被两个真实问题逼出来的：

1. **Bing 的图片端点只认特定尺寸**：`_800x450` 返回 404，`_1920x1080` 才可用。
   缩略图 URL 直接用它就会整片空白。
2. **浏览器直连第三方图床可能被防盗链拦掉**，且无法加 Referer。

代理还带来两个好处：磁盘缓存 → **断网也能看**；重复请求 **0.012s vs 0.16s（快 30 倍）**。

## 缓存策略

```
.cache/feed.json      条目列表（含署名与来源状态）
.cache/images/<sha1>  图片二进制
```

- `autoRefreshHours`（默认 12）内直接用缓存，**首页秒开**
- 全源失败时**保留旧缓存**并标记 `degraded` —— 宁可展示昨天的，也别展示空白
- 单个源失败不影响其它源

## 配置

`site/feed.config.json`：

```json
{
  "sources": ["bing"],
  "count": 8,
  "query": "travel",
  "autoRefreshHours": 12,
  "keys": { "PEXELS_API_KEY": "", "UNSPLASH_ACCESS_KEY": "" }
}
```

**默认只启用 bing**：题材是风景/人文/时令，与文旅对口且每天更新。
picsum 是通用摄影图（大量办公/静物），放在文旅站点里会显得不搭，默认关闭。

key 只存在这个文件或环境变量里，**不进前端、不进仓库**。

## 前端注意

- 灵感图**不要加 `loading="lazy"`**：实测加了之后屏幕外的图不加载，
  截图/首屏会出现整片空白。16 张图直接 eager 加载没有性能问题。
- 标题与署名必须同时展示 —— 只放图不标来源是不行的。

## 已知限制

- 没有按时自动刷新的定时器（只在请求时按年龄判断），需要外部定时任务触发
- 图片缓存的清理挂在 `/api/cleanup` 的 rules 之外，暂未纳入自动清理
- Pexels / Unsplash 的适配器代码已写好但**未实测**（缺 key）
