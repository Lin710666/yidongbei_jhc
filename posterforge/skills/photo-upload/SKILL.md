# Skill: photo-upload（照片上传与校验）

## 什么时候用

任何"要用户给图"的场景：游客打卡的照片、酒店实拍图、菜品图、客户提供的 logo 与素材。
**这是 `tourist-checkin` 真正可用的前提** —— 没有它，打卡卡只能用占位图。

## 设计决定：为什么用 base64 JSON 而不是 multipart

Node 内置模块**不解析 multipart/form-data**。要用 multipart 就得引入依赖，
而本项目的硬要求是"零运行时依赖，解压即跑"。

代价是 base64 会让传输量膨胀约 33%。对本地部署（回环网络）来说，
这点开销远小于多一个依赖树的维护成本。

```json
POST /api/upload
{
  "files": [
    { "name": "我的打卡照.png", "dataUrl": "data:image/png;base64,iVBORw0KGgo..." }
  ]
}
```

响应：

```json
{
  "ok": true,
  "files": [
    { "name": "我的打卡照.png", "file": "mugigfzu-q4mx2-我的打卡照.png",
      "url": "/uploads/mugigfzu-q4mx2-我的打卡照.png",
      "bytes": 60727, "mime": "image/png" }
  ],
  "errors": []
}
```

## 安全校验：只信真字节，不信声明

客户端声明的 MIME **可以伪造**。所以服务端按魔数判断：

| 格式 | 魔数 |
|---|---|
| PNG | `89 50 4E 47` |
| JPEG | `FF D8 FF` |
| WebP | `RIFF....WEBP` |

实测：一个把 `this is not an image` 文本 base64 后、声明 `image/png` 的请求，
被拒绝并返回 `"不是 PNG / JPEG / WebP（已按字节校验）"`。

其它限制：
- 单文件上限 **12 MB**（手机原图足够）
- 单次最多 6 张
- 文件名做白名单清洗（保留中文、字母、数字、`.`、`-`、`_`），并截断到 60 字符

## 上传之后：路径怎么进 spec

这是**容易踩的坑**：上传的文件在 `site/public/uploads/`，
而渲染器默认相对 `poster-forge/` 解析图片路径 —— 直接写 `uploads/x.png` 会报"图片不存在"。

解决办法是渲染器支持**多个图片搜索根**：

```python
# poster-forge/render.py
IMAGE_ROOTS = [HERE]                      # 默认只有自己
# 站点通过环境变量注入 public/
#   PF_IMAGE_ROOT=E:\deepseck\site\public
```

解析顺序：**注册的根优先于 poster-forge**，绝对路径直接返回。

所以 spec 里写相对站点的路径即可：

```json
{ "type": "image", "name": "photo", "src": "uploads/mugigfzu-xxx.png" }
```

`validate.py` 的图片存在性检查也走同一个解析函数，
避免出现"上传成功但校验不通过"这种自相矛盾的状态。

## 多图网格（1/2/3/4 张）

上传多张照片时，打卡卡按数量自动排布：

| 张数 | 布局 | 间隙 |
|---|---|---|
| 1 | 单图大图 | — |
| 2 | 2×1 并排 | 0.015（≈60px @1080） |
| 3 | 3×1 一排 | 0.015 |
| 4 | 2×2 网格 | 0.015 |

**边框策略**：只有单图用统一外框，多图一律每张各自描边。
原因是圆角半径不匹配 —— 外框半径 38 与图片半径 ~20 不一致，
框线会在角上切过图片，看起来像排版事故。

渲染器另外支持 `image` 图元的 `tiles` 字段（把**一张**图切成 N 格），
用于多房型/多菜品的同图切分场景；与"多张不同照片"是两回事。

## 前端约定

- 选择文件后**先占位显示**（`⏳ 文件名`），让用户立刻有反馈
- 上传成功后 chips 变金色边框，并显示 `已上传 n/m`
- 被拒文件显示 `⚠ 被拒 n 个`，鼠标悬停看具体原因
- 支持拖拽、点击、**Ctrl+V 粘贴**三种入口
- 上限 6 张，超出部分不接收

## 交付判定

- [ ] 上传后 `uploads/` 下能看到文件，且字节数与源文件一致
- [ ] 打卡卡生成结果里显示"使用上传照片"（而不是"未上传照片，使用占位图"）
- [ ] 伪造文件被拒绝
- [ ] 超过 12 MB 的文件被拒绝并给出明确原因

## EXIF 方向处理（已实现）

**问题**：手机竖拍的照片实际存成横向 + 一个 `Orientation` 标签。
不做处理会**横着进打卡卡**——用户一眼就能看出错了。

三处都需要正确方向，所以做成两段式：

| 阶段 | 做法 | 目的 |
|---|---|---|
| 上传落盘时 | PIL `exif_transpose` 转正并**丢弃全部 EXIF** | 预览正确、顺带去掉 GPS 等隐私信息 |
| 渲染时 | 渲染器自己再过一遍 `exif_transpose` | 兜底：手工放入的图或归一化失败的图也正确 |

实测：`800×600 + Orientation=6` 上传后变成 `600×800` 且 EXIF 为 `None`；
渲染出的打卡卡里方位标记位置与期望完全一致。

**为什么不在 JS 里做**：浏览器通过 `createImageBitmap` 已应用 EXIF，
拿不到原始方向；Node 侧也没有 EXIF 处理能力。PIL 是干净解法。

## 目录清理（已实现）

```powershell
# 查看各目录占用与保留规则
Invoke-RestMethod http://127.0.0.1:8787/api/storage

# 手工触发清理
Invoke-RestMethod http://127.0.0.1:8787/api/cleanup -Method Post
```

保留规则是**双条件**：`maxFiles` + `maxAgeDays`，两个都满足才删。

| 目录 | 数量上限 | 天数上限 |
|---|---|---|
| `uploads/` | 200 | 30 |
| `generated/` | 200 | 7 |
| `copybooks/` | 100 | 30 |

**⚠ 取舍要清楚**：数量上限只在文件同时过期时才生效，
所以**磁盘占用没有硬上限**。好处是绝不会删掉用户刚上传的文件
（那比占空间严重得多）；代价是密集使用期间目录会持续变大。
用 `/api/storage` 观察增长，必要时调小阈值。

已用四种场景验证策略：超量且过期（删）、未超量（留）、超量但新鲜（**不删**）、
全过期且超量（删到上限）、边界正好等于上限（不删）。

## 已知限制

- **无图片编辑**：不裁剪、不旋转到任意角度（EXIF 方向已自动处理）
- **无缩略图**：预览用原图，多张大会拖慢页面
- **无自动定时清理**：需要外部定时任务调用 `/api/cleanup`
- **无病毒扫描**：本地单机场景可接受，对外提供服务则必须补
- **人像照片的肖像权**由使用者自行确认，技术上不做检测
